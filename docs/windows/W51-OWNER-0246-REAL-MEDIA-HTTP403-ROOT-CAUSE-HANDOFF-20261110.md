## The PHP server's exact AUDIO 403 conditions (SOURCE CODE, NOT YET live-body verified)

`server/src/Application.php`: GET/HEAD numeric route `/api/v1/audio/{replacement_id}` enters `server/src/Http/AudioController.php`.

`AudioController::handle()` issues 403 JSON only when:
1. `sid` query parameter exists but is invalid in syntax → `invalid_audio_token`.
2. `AudioTokenService::valid(replacementId, row.version, expires, token, sid)` fails → `invalid_audio_token`. This checks expiry (must be future, within TTL), hex HMAC-SHA256, exact replacement ID, version and session ID (if given).
3. `sid` present but `AudioAccessService::allowed(sessionId)` false → `access_denied`, rechecking session status and entitlement on every audio Range.

`server/src/Application/ResolveService.php` builds the signed URL using **replacement ID, version, expiry and optional session ID**; the 403 can happen even though `RESOLVE_APPROVED` and `SOURCE_MAPPED` are true. `windows-companion/w15/Celikom.Companion/GrantValidator.cs` and `windows-companion/w15/source-controller.mjs` validate the URL's token/expires/sid shape and expiry before mapping, **but that validates the granted URL, not the URL Chromium actually fetches**. `windows-companion/w22/native-resource-adapter.mjs` passes validated signed URL into `downloadInfo.urls[0]` and `downloadInfo.url`.

**Unproven exact culprit:** owner TXT purposefully redacts full media URL/query, headers and error body. Cannot determine whether native Yandex's media core discarded/modified `?token=&expires=&sid=`, the server rejected session entitlement/signature/version, or a host/WAF/proxy itself produced a different 403. Hypothesis of lost/modified query is plausible and worth testing FIRST because W48's independent renderer fetch using the granted signed URL returned **206** for approved sources, while W50's **real native media GET** receives **403** within a second of mapping. **Do not claim this hypothesis as fact**. Independent probe may differ in request context, and the live server error response was not captured. Missing CORS events alone doesn't distinguish PHP vs CDN/WAF.

**Supported core conclusion:** approved replacement audio fails at **actual native media HTTP authorization/serving stage (403)** before a playable audio stream; the source mapping and independent MP3 byte probes are NOT audible success. Changing bitrate to nominal 320 in W50 did NOT fix real playback. Unrestricted CORS, returning unauthenticated MP3, copying encrypted `key/iv`, re-implementing a separate player, or changing unrelated Android/Test.50 are **NOT acceptable fixes**.
