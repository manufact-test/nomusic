## W110: independent process, not another consumer app
- New .NET Windows helper: `windows-companion/w15/Celikom.UpdateSupervisor/` (Program, UpdateSupervisorEngine, WindowsSupervisorHealthProbe). Internal helper of the same installed CELIKOM, not a parallel player, test product or alternate installation.
- Program only accepts `--supervise` + exact transaction GUID, enforces a single supervisor per transaction, fixed LocalAppData rollback root, an embedded signer certificate fingerprint and a bounded 35-minute process lifetime.
- **The production signer pin constant is intentionally EMPTY.** Production startup exits code **3** before touching journal or running installers. CI tests this exact block. No command-line, environment or unsigned feed parameter can supply a replacement pin.
- The core reads W109's DPAPI journal separately from the GUI. Detects verified target process/version then checks local bridge using a valid token via localhost `/v1/state`, never tries to authenticate to Yandex or read audio. Reads session DPAPI without generating a replacement. Checks native module identity read-only.
- If the target is not healthy within the journal's 10-minute window, records `RollbackNeeded`. NEVER terminates the app, Yandex or playback. Only if neither Yandex nor CELIKOM is running does it reverify the cached previous signed installer and record the one recovery attempt DURABLY before invoking the normal same-AppId Inno update path. Recovery has a NEW 10-minute health deadline; failure/timeout leads to `ManualRecovery`, never another downgrade loop.
- W110 simulated contract tests: 17 cases, including GUI never starting, no false healthy from EXE start, auth bridge/native failures, owner still playing, corrupted/missing old setup, failed installer, incorrect transaction, and one-shot restored old version. Windows CI compiles helper with warnings-as-errors and runs simulation. These tests use fake probes/launchers; **NOT a real app/installer end-to-end field test**.

## W111: original DPAPI account witness
- New `SignedUpdateSessionIdentity.cs`: read-only decrypt of existing `session.dpapi`, never `LoadOrCreate`, fingerprint SHA256 of canonical installation GUID + lowercased account email. A legitimately refreshed access token does not change identity.
- W109 `StableUpdateRollbackJournal.Record.SessionIdentitySha256` stores this hash inside user-scoped DPAPI protected journal. `PrepareSigned` refuses preparation if an expected existing session cannot be read; `PrepareCore` and journal validation reject missing/invalid session evidence when `ExpectedSession=true`.
- External W110 probe compares currently present account fingerprint against the journal, instead of reporting any readable new session as preserved. The supervisor refuses missing witness. CI tests absence, token rotation, installation-id replacement, account switch, encrypted-session corruption, and simulated new account failing health.
- Witness is a preservation check, not an account secret or new login. No tokens are persisted outside the existing DPAPI store.
