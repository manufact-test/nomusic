# Первое сообщение для следующего чата — CELIKOM Windows W51

Продолжаем **существующий CELIKOM Windows**, не начинай заново. Ты новый ведущий разработчик.

**GitHub:** `manufact-test/nomusic`
**Рабочая ветка:** `experiment/windows-companion-integration-20261108`.
**Основной разбор последнего теста:** `docs/windows/W51-OWNER-0246-REAL-MEDIA-HTTP403-ROOT-CAUSE-HANDOFF-20261110.md`.

**Установлено у владельца:** CELIKOM **0.24.6**, GUI/native совпадают. Обычные треки играют; подменяемые быстро переключают Play/Pause, не играют и остаются на паузе. Последняя реальная диагностика пользователя — `CELIKOM-diagnostics-20261110-114109.txt`.

**ГЛАВНАЯ НОВАЯ НАХОДКА W51:** W50 убрал собственные диагностические запросы. Теперь CDP показывает **настоящие запросы Yandex Media**: `7 GET`, **все 7 HTTP 403**, ресурсы `/api/v1/audio/139` (4) и `/api/v1/audio/89` (3). `PLAYER_NET_CORS_BLOCKED=false`; `PlayerAudibleEventObserved=false`. Эти `139/89` — **replacement_id / audio resource IDs, НЕ Yandex track IDs**, хотя W50 ошибочно называет их `track=...`. `SOURCE_MAPPED` есть, но это не воспроизведение. В момент первого 403 для ресурса 139 только что был замаплен Yandex track `42498653`. Не приписывай `PLAYER_ENGINE_FAST_PAUSE` подмене: в логе эти события были ДО первого замапленного подменного трека.

В серверном `server/src/Http/AudioController.php` 403 означает `invalid_audio_token` (параметры `token/expires/sid`, HMAC, TTL, версия) или `access_denied` (права привязанной сессии); нельзя исключать 403 от хостинга/WAF. Ранее независимый 32-байтный fetch того же типа подписанных ссылок давал 206, но реальный Yandex Media GET даёт 403. **Гипотеза:** Яндекс теряет/меняет query подписанного URL при собственной загрузке; **не доказано**, так как диагностика правильно скрывает URL и тело 403.

**Следующий большой заход, без остановок:**
1. Исследуй `ResolveService.php`, `AudioTokenService.php`, `AudioController.php`, `GrantValidator.cs`, `w22/native-resource-adapter.mjs`, `w23/host.cjs`. Установи, отличается ли фактически запрашиваемый URL от того, который мы выдали Яндексу.
2. Подготовь privacy-safe наблюдение в тестовой ветке: сравнивай полный ожидаемый и реальный URL **только в памяти**, логируй лишь `exact_match/query_missing/query_changed/expired`, без токенов, sid, ссылок, заголовков, ответов. Сравнивай по replacement_id, а не по Yandex track_id. Отличай 403 `invalid_audio_token`, `access_denied` и upstream/WAF безопасным способом.
3. Исправляй **подтверждённую** причину, не ослабляя подпись, entitlement, CORS или безопасность. Сделай тесты + изолированную проверку на настоящем подписанном Яндекс-клиенте с восстановлением оригинальных файлов.
4. **Не делай новую сборку пользователю ради пустой диагностики.** Только после доказанной причины и успешного CI. Обновление 0.24.6 → следующая версия строго поверх, 1 приложение, без потери входа. Файл отправляй **через Библиотеку ChatGPT (CELIKOM/Windows) и рабочую прямую карточку файла в чате**, а не битые sandbox-ссылки.
5. Android/Test.50, продакшен/API и оригинал Яндекса не трогай без отдельной причины/разрешения.
