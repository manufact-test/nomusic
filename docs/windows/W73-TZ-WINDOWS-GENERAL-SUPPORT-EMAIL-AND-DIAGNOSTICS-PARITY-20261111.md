## 3. Как РЕАЛЬНО устроены расширение и сервер; не выдумывать
**Браузер 0.4.76:**
- Для общего сообщения `support.ts` собирает короткий `buildSupportReport`; отправляет `kind:"general", message, request_key, report`; auth-broker превращает `report` в **`support_diagnostics`** в `POST /api/v1/support`.
- Для жалобы на песню `kind:"song"` + `report:buildSongReport(...)`. Обязательна актуальная песня. Используется тот же конечный API, но другой тип тикета.
- На неоднозначный результат сохраняются текст, UUID `request_key` и **то же диагностическое вложение** для точного повтора; после подтверждённого ответа очищаются.
- Серверная админка показывает `Техподдержка → обращение → Скачать диагностику JSON`; права только owner/moderator. Удалён инлайновый блок «Техническая диагностика», оставлена только скачиваемая вложенная JSON.

**Windows 0.24.20:**
- `CompactSendSupportAsync` УЖЕ создаёт и кэширует автоматический `DiagnosticLog.ExportSupportSnapshot` и при обычном обращении вызывает `SendSupportAsync(..., diagnostics: snapshot)`; для song — `SendSongSupportAsync(..., windowsDiagnostics: snapshot)`. Жалоба на песню по живому отзыву владельца приходит с диагностикой.
- Windows general передаёт поле **`diagnostics`** c `platform:"windows"`, не `support_diagnostics`. Это **не обязательно баг**: активный API в `server/src/Application.php` специально поддерживает оба конверта — `support_diagnostics` (Chromium/Android) и старое `diagnostics` **только для Windows**. `SupportService` нормализует Windows-снимок и хранит в `support_tickets.report_json` как приватное вложение. Не ломать совместимость, пытаясь слепо переименовать ключ.
- Windows показывает «Сообщение отправлено» после успешного API-запроса. Этот статус **не означает, что письмо доставлено**: SMTP выполняется отдельной серверной стадией.

**Письма по уже существующему контракту:**
- При **создании general** `SupportService::create` сохраняет тикет и запись в `support_messages` с `mail_required=1`, планирует SMTP-уведомление **на адрес поддержки**, выбираемый через `config['mail_from']`. `SmtpMailer::sendSupport($to, ticket, body, true)` формирует «Новое обращение CELIKOM №…».
- При **ответе owner/moderator из админки** `SupportService::reply` добавляет сообщение в тот же тикет и отправляет письмо **на email пользователя** из `users.email`, с текстом «Ответ поддержки CELIKOM №…». Исходящая отправка не является автоматическим подтверждением при создании заявки.
- При **жалобе song**: `mail_required=0`, SMTP-уведомление/ответ по почте **не требуется по текущему контракту**. Сообщения и диагностика видны в админке.
- В `SupportService::deliver` `delivery` становится `sending`, затем `sent` при SMTP 250, а на исключении — `unknown`. **`unknown` не доказывает фактическую недоставку**, а означает неопределённый результат. Намеренно нет слепого автоматического resend после неоднозначного SMTP во избежание дублей. Возможна отложенная задача через `support_after_response`.
- Текущий продукт **не обещает автоматического email пользователю сразу после подачи general**. Если пользователь под «ответом по почте» имеет в виду именно такую квитанцию, сначала фиксировать отличие от расширения, а не добавлять неподтверждённую функцию.

Посмотреть существующее тестовое `general` обращение владельца (при наличии и с разрешённым доступом), установив по нему `ticket_id`, `kind`, `report_json` и цепочку `support_messages.delivery / mail_required / admin_id`. Ни в отчёте, ни в GitHub не публиковать пользовательские email, токены и SMTP-конфиг.
2. Дополнительно провести **разрешённый end-to-end живой тест** с реальным inbox поддержки и реальным тестовым аккаунтом после безопасной подготовки; проверить вручную получение, не только `sent`.

## 5. Критерии приёмки
- General из Windows → один `ticket_id`, **в админке полный текст и доступный owner/moderator `Скачать диагностику JSON`**, обычный клиент не видит private report.
- Подтверждён реальный email-уведомление поддержке **о новом general** (если именно это ожидается) и реальное письмо **пользователю только после admin reply**, с корректным отправителем и номером тикета. Владелец может сообщить, какой из этих двух ожидаемых писем он не видит, только если аудит не позволяет это установить.
- Письмо содержит только безопасный текст, **не приватный JSON**. Email пользователя/адрес поддержки берётся из действующей защищённой конфигурации/БД, не из инъекции клиентского payload.
- Песенный report по-прежнему сохраняет диагностику, обрабатывается без обязательной email-переписки; сохранена защита от дублей.
- При неуспешном SMTP сообщение не пропадает, интерфейс не выдаёт ложного обещания «письмо доставлено», повтор отправки не порождает дублей.
- Не ухудшены Start/Stop, музыка, пауза/перемотка, MyWave, 0.24.20 сетевое восстановление и подписи/защита Yandex. Никаких заявлений «всё исправлено» только по зелёному CI: нужен живой тест.
