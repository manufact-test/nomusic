## What is concretely reusable for Windows
1. **Stage boundary ≠ playable output.** Android separated FileInfo method discovery / DTO conversion / decoder source selection / MediaSource prepare / audible Play. Windows logs `RESOLVE_APPROVED` → `SOURCE_MAPPED` but 4/4 independent audio probes `AUDIO_PROBE_FETCH_BLOCKED`; still no demonstrated HTTP 206, decoded PCM, audible play, or pause acknowledgement. Do NOT treat mapping as an audio fix. Add future redacted diagnostic stage markers for actual renderer/transport/decoder *only when observable*, and mark unknown as NOT_OBSERVED.
2. **Source descriptor and crypto compatibility.** Signed Android DTO contains `urls, codec, bitrate, key, quality, gain, r128`. This does NOT establish that the Windows Electron/JS file-info response uses the same field semantics. But our Windows `toDownloadInfo` deletes `key` and `iv` and forces `codec`, `transport:'raw'`, `gain:false`, `urls:[url]`, `url`. This is a separate **potential** decoder/contract mismatch: a technically valid external URL or successful response may still be rejected by the original native player. First observe the **actual Windows original file-info shape and decoder expectations** in isolated tests, using schema flags/field-presence only; never log account keys, signed URLs, auth headers or DRM values. Do NOT indiscriminately restore keys/IV (could instruct decryption of a raw MP3), nor blindly strip them, change transport, or synthesize metadata to make it "fit."
3. **Exact track+edition+generation.** Android models fail-closed binding current playback generation + exact track ID + edition to one source *before prepare*, rejecting late Next/radio responses. Windows validates numeric track IDs and has generation cancellation, but does not independently prove requested ID = currently audible edition or chosen decoder source. Test this binding at the genuine Windows player handoff; no display-title matching, approximate ID, uncontrolled delayed remapping.
4. **Single original Yandex clock.** Android's old two-player Test.74 had Pause/Seek delays for RASKOL 42884423 and Dym 39949113 (remote Media3 lag 3.1–3.3 seconds), and audible join click. This is evidence that **second audio clock / post-start blend is unsafe**; it is NOT the cause of the current Windows immediate pause (Windows retains original native player). Preserve Windows source-only approach; do not "fix" it by injecting a second audio player, crossfade or external media controller.
5. **Buffer/runway/Range must be proved separately.** Android cold starts exposed sparse/insufficient buffer and seek failures. For Windows once fetch is actually allowed, verify signed 206 + Content-Range + mime/first-bytes + key/codec expectations + sufficient contiguous data before giving the source to Yandex. The independent 32-byte probe only establishes network visibility and format header, not a compatible stream for the native decoder.
6. **Original control before clone/change.** Android emulator latest CI couldn't keep even untouched original control process running. In Windows, independently compare (a) unchanged signed native Yandex, (b) installed CELIKOM native host with substitution OFF, (c) approved source ON. One platform's "CI green" never substitutes for audible owner playback.
