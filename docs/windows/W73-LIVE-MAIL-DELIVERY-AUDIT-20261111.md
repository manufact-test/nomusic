Чужие письма, тело сообщения, пользователя и credentials не скачивали и не выводили.

### Значение для проблемы владельца
- Уведомление **о новом general** идёт на защищённый **Gmail-ящик поддержки**, адрес определяется `CELIKOM_MAIL_FROM`, а не в произвольный личный email. Две проверенные реальные заявки в этом ящике есть. Если владелец смотрел другой аккаунт или клиентскую почту, он не увидит эти уведомления там.
- **Автоматическая квитанция пользователю после отправки general не реализована ни в браузерном расширении, ни в Windows.** Это действующий согласованный контракт, не сбой доставки. Клиенту отправляется письмо после **ответа администратора**, на `users.email`; в БД два таких ответа имеют `delivery=sent`. Реальное появление **админских ответов в индивидуальных inbox получателей** отдельно не проверялось: доступов к тем ящикам нет. Двусторонняя SMTP-проба подтверждена, но не подменяет подтверждение получателя.
- Подтверждение Windows `Сообщение отправлено` означает, что API создал/вернул `ticket_id`; не гарантирует почтовую доставку. Счётчик `sent` сервера означает SMTP 250, но мы дополнительно проверили **факт помещения обоих реальных входящих писем в Gmail Inbox**.
- Не утверждать без данных, что у владельца отсутствует письмо именно из-за просмотра другого ящика/ожидания автоквитанции: это вероятные варианты, окончательно различаются уточнением, какого письма он ждал. Потеря этих двух уведомлений в Gmail исключена фактической проверкой.

### Что проверено / что не делали
- W72 CI 42998876460 уже проверил Windows/support tests, UUID dedupe, приватный JSON, ACL, песенный вид обращения и сохранение диагностики на disposable MySQL, без реального SMTP. Владелец сам подтвердил song + JSON из установленной 0.24.20. W73 live SMTP/Gmail добавляет недостающую почтовую проверку; никаких изменений в Windows, музыке, оплате, admin PHP и prod DB не вносилось.
- Не создавали реальных user-тестовых записей и не пересылали ни одного клиентского текста или отчёта по почте. Read-only SQL; временные скрипты для SMTP-пробы загружались в приватный incoming и удалялись по exit trap. В workflow отсутствуют логи с email/паролями.
- Никакой server redeploy, новая сборка EXE, замена `Application.php`/админки или изменения SMTP адреса не выполнялись.
- **Для окончательного закрытия пользовательской стороны ответа** следует увидеть хотя бы одно письмо от поддержки во входящем ящике адресата после реального admin reply; к чужому inbox у разработчика нет доступа. В остальном рабочий маршрут уведомлений о `general` подтверждён до Gmail Inbox, а не только тестами.
