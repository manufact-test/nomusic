## Two bounded changes
1. **RASKOL/Dym alternative user transport inside Android shade:** four explicit user buttons `Пауза/Играть`, `−30 с`, `+30 с`, `Следующая` added only when CELIKOM is signed-in, armed, connected and the actual source track is READY as ID 42884423 or 39949113. Android notification invokes our **non-exported service** via immutable explicit PendingIntent with run+track alias+track ID guards. It sends `pause()/play()/seekTo()/seekToNextMediaItem()` to the **existing Yandex Media3 controller** only when corresponding Player command available. Logs `problem_transport_command_sent`, `problem_transport_command_unavailable` or `problem_transport_command_failed`, followed after 250ms by passive `problem_transport_command_observed` readback. **No audio-owner, PCM, DSP, source session, native seek, manifest permission, root/Accessibility/NotificationListener changes.** This creates a practical alternative path independent of Yandex *UI* dispatch, but is still dependent on Yandex permitting *remote Media3 transport commands*. It is NOT VERIFIED on HONOR until the user tests buttons. Existing Yandex UI pause/seek remains technically unfixable when no event is emitted: do not misrepresent this as a proven native UI fix.
2. **Cold random song foreground priority:** while the current **sparse decoder** is waiting for its verified clock/runway handover and current sound is not yet owned by CELIKOM, reserve the existing single pending-next slot instead of initiating full-file speculative NEXT transfer. It flushes after the existing successful current handover through `flushPendingNextAfterJoin()`. The normal full-file prefetched known-next path, all cached-next cases, source boundary/generation guards and previously accepted crossfades stay unchanged. Expected benefit only in cases competing for network while current buffer/clock is preparing. This is an **experimental speed fix**; HONOR proof pending.
