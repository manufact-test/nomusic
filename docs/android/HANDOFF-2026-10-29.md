## 1. Главное для следующего разработчика

Проект НЕ принят пользователем как стабильно работающий. Было много выпусков с частичными исправлениями и повторными жалобами. Последняя выданная версия — **0.3.43 / versionCode 44**. После её выдачи пользователь не подтвердил результат: он попросил передать работу другому чату. Не писать «всё исправлено» на основании этого документа или зелёных тестов.

Пользователь сообщает, что до усиления защиты всё работало лучше и что после него снова появились срывы, резкие переходы, чужие фрагменты и отказы определения. Нельзя исключать эту связь только потому, что несколько файлов движка не менялись. Подтверждены и конкретные ошибки этого чата: проверка диагностики в очереди воспроизведения, исправление в исходниках без него в отправленном APK и чрезмерно строгий контроль синхронизации, создававший циклы сбросов. Полная причинная цепочка первоначального ухудшения НЕ установлена.

Сейчас задача — восстановить устойчивое воспроизведение на телефоне, сохранив работающую компьютерную версию и согласованную защиту. ## 3. Как собирается APK

Это не обычный Gradle-проект с полной пересборкой всех исходников. Java-addon компилируется и заменяет `classes2.dex` в проверенном базовом APK **0.3.22**. Сохраняются его оригинальные компоненты/ресурсы/каталог; скрипт меняет согласованные свойства manifest и закрывает старый launcher. Остальная нативная часть находится в базовом APK. Это важно для анализа аудиосессий и соответствия пакета исходникам.

### Инструменты и входные данные

- JDK 17; используется `java com.sun.tools.javac.Main`.
- Android SDK API 36; JAR из `platforms/android-36/android.jar`.
- Apktool 2.11.1, Android build-tools с D8, zipalign, apksigner.
- Пять закреплённых JAR в `android/native-companion/deps/`, исключённых из Git. Хеши/официальные координаты — в `build-inputs.json`; `json.jar` нужен для host-тестов, не для упаковки Android.
- Базовый APK `CELIKOM-0.3.22-install.apk`, SHA256:
  `170b1883e292570d28a3b5c619cf000eaccd9d11ee85ca6f6c08f7b50e5f72c9`.
- Исходный факт восстановления 0.3.22: `RECOVERED-0.3.22.json`; тогда пересобранный `classes2.dex` был побайтово идентичен установленному.
- Подпись хранится **вне Git**. Локально: `/workspace/scratch/8ea214c841d3/integration/private/`, файлы `celikom-native-probe.p12` и `signing.json`. Не печатать содержимое, не прикладывать и не коммитить. Каталог 700, файлы 600. Если путь исчез — приватная резервная копия называется `CELIKOM-Native-Signing-Private-Backup.zip`; получать через доступ пользователя к файлам, не публиковать архив.
- Нельзя генерировать другой ключ. SHA256 сертификата:
  `67fe81c56fac1c1d145344b69a0e3faf9005cf6607f4e26ca27d5926c3eefc4f`.

В существующем окружении, из корня **Android-checkout**:

```bash
python3 android/native-companion/build_release.py \
  --sdk /workspace/scratch/8ea214c841d3/android-build/sdk \
  --build-tools /workspace/scratch/8ea214c841d3/android-build/sdk/build-tools/android-16 \
  --apktool /workspace/scratch/8ea214c841d3/tools/apktool.jar \
  --base-apk /workspace/scratch/8ea214c841d3/recovered31/CELIKOM/CELIKOM-0.3.22-install.apk \

  --output /workspace/scratch/8ea214c841d3/outputs/CELIKOM-0.3.43-install.apk
```

Название папки build-tools `android-16` — существующий локальный путь, не требование собирать под API 16. В другом окружении заменить абсолютные пути действительными. Если зависимости/базовый APK/ключ отсутствуют, сначала восстановить входные данные; не заменять их непроверенными файлами.

Для нового выпуска повысить согласованно `AppVersion.NAME`, `VERSION`/`VERSION_CODE` в build-скрипте и ожидаемые versionName/versionCode в verify-скрипте. Последний versionCode — 44. Обновление ставится поверх, без удаления аккаунта/настроек приложения. Скрипт с 0.3.42 сам создаёт свежий уникальный каталог сборки; не возвращать общий старый каталог ради ускорения. Не менять Java-файлы параллельно сборке.

### Точный объём изменений защиты 0.3.34

1. `DiagnosticAccess.java`: два SHA256 нормализованных email в исходнике. Только активная личность из свежего аутентифицированного `/auth/me`. Промокод/обычная подписка не предоставляют административный экспорт. Адреса не публиковать; сверять две константы в коде, не придумывать новые аккаунты.
2. `NativeApi`: grant привязан к accountGeneration, действует 60 с; refresh запрашивается раз в 45 с. Ошибка сети не создаёт/продлевает право. Login/logout/смена аккаунта сбрасывают состояние.
3. `LogStore`: запись/полный экспорт ограничены этим правом, секреты редактируются; при logout/отказе и первой privacy-миграции очищаются приватные журналы/подготовленные TXT. Истечение lease может давать пробелы в записи, поэтому отсутствие событий не доказывает отсутствие сбоя.
4. `RecorderActivity`: право проверяется до snapshot, до системного сохранения и при копировании файла. Отображаемая подсказка владельца не является разрешением.
5. `IdentityEntry` и smali `MainActivity.onCreate`: закрыт обход через `legacy_tools`; старый launcher перенаправляется в актуальный экран и завершается. Нативный подтверждённый equalizer/session путь сохранён. При аудите декодирован старый launcher: убранный вызов `PublicMediaProbe.shared` создавал observer; его причинная связь с жалобами не установлена.
6. `ProbeService`: OPEN/CLOSE_AUDIO_EFFECT broadcast extras больше не считаются доказательством отправителя. На API 34+ сравнивается UID; на Android 13 они только наблюдаются. Реальная потеря control эффекта и подтверждённая equalizer-сессия остаются значимыми. Этот путь требует физической проверки и не доказан безопасным для всех маршрутов одним unit-тестом.
7. Сборка удаляет `assets/identity-integration-source.zip`; при восстановлении ZIP Apktool из unknown-list его также исключают при финальной пересборке архива. Проверка должна запрещать исходники, source maps и ключи в APK.

Это локальное ограничение официального клиента, **не серверная роль администратора и не защита от декомпиляции/модификации клиента**. Новый серверный механизм административных прав не развёрнут. Подробной сертификации безопасности всей инфраструктуры не было. 25.10 репозиторий был публичным; пользователя предупредили о необходимости приватности. Не считать прошлые копии исходников отозванными. Текущую видимость проверять при необходимости.

## 5. Что исправляли, что потерялось, что остаётся

### Подтверждённые дефекты и проверки

- Проверка диагностики блокировала очередь поиска/авторизации песни: устранено разделением сетевого ожидания в 0.3.36. Тест блокирует диагностический запрос и проверяет работу очереди следующей песни.
- «Монпасье»: streaming seek был сброшен через 2 с, затем вся запись 9,5 МБ загружалась ещё 52,9 с; подключение заняло около 66,4 с. 0.3.38 устранил преждевременный срок для частичного потока, не гарантируя мгновенную связь на любой сети.
- Очистка BufferedAudio могла начинаться до остановки старого MediaPlayer. В 0.3.39 порядок изменён; новый тест падал до исправления. В последующих отчётах `replacement_output_silenced` показывает zero/paused до cleanup, но не измеряет звук Bluetooth.
- «Было давно»: первоначальный seek 3400 мс, корректирующий 1784 мс; поздний старт, затем дополнительная слышимая перемотка. 0.3.40 воспроизвёл и исправил этот допуск к audible-переходу.
- «Он рядом»: Яндекс сообщает `Quest Pistols Show, Quest Pistols`, каталог альбома — `Quest Pistols`, название и длительность 224520 мс совпадают. Исправление сужено до наблюдаемой дублированной пары, не удаляет произвольного дополнительного исполнителя. В отчёте 0.3.42 песня уже определяется как ID89285816 и сервер находит replacement39.
- 0.3.42 определяет и остальные песни, но warm-alignment с порогом 80 мс сам вызывает `alignment_unstable`: «Легко ли быть молодым» сброшена дважды; «Розовое вино» — пять раз. 0.3.43 согласовал этот контроль с допуском 350 мс. Повторные resolve/download отсутствуют в host-воспроизведении девяти записанных начальных расхождений. Это не физическая приёмка 0.3.43.

### Что действительно «потерялось»

Подтверждена потеря **исправления AlbumMatch в отправленном APK 0.3.41**. Готовый APK восстановлен из сохранённого файла, хеш совпал с квитанцией, декомпиляция показала отсутствие `artistKey`. В Git-коммите `ab2266fd2b97d79e62af7702d1163b1447860e18` этот метод есть. Весь APK не был просто старой версией: версия и часть новых компонентов присутствовали. Точный механизм появления устаревшего класса не восстановлен; утверждение «это точно только кеш сборки» было бы догадкой.

Сравнение исходников 0.3.33 и 0.3.36 показало побайтовое равенство шести файлов: ReplacementEngine, BufferedAudio, AudioTransfer, SyncPolicy, SourceTransitionGate, ApiContract. Прежние исправления хвоста/границ/паузы существуют в текущем исходнике. Это **не доказывает**, что поведение не изменилось через сервис, auth, логирование, упаковку или другой код; и не является независимой проверкой всех старых APK.

### Открытые вопросы

- Фактическая плавность переключения оригинал/подмена на HONOR 50, особенно Bluetooth и мобильная сеть, не подтверждена. Unit/host-тесты используют заглушки Android/audio; их зелёный результат не равен звуковой записи/замеру на устройстве.
- Пользователь слышал начало другой песни, странные окончания и провалы. Единого доказанного объяснения всех этих жалоб нет. В ряде экспортов естественный конец «Папирос» не попал в текущий run; нельзя объявлять жалобу ошибочной или требовать отчёт каждую секунду.
- При известной песне подготовка/авторизация всё ещё требуют сети. Следующая песня не всегда подготовлена заранее, поэтому сначала может звучать её оригинал, затем подмена. Архитектура пока не гарантирует незаметный переход как в компьютерном расширении.
- Yandex anonymous `albums/{id}/with-tracks` ранее возвращал **451 REGION_RESTRICTION** на части IP/VPN, хотя нативный Яндекс проигрывал песню. Серверный fallback не реализован и не развёрнут. Это отдельная проблема; не приписывать каждый новый отказ VPN.
- Были шумные скачки позиции источника примерно на 2,6 с назад («Всё пиздато»); отдельное надёжное подавление таких ложных скачков не реализовано. Настоящие пользовательские seek игнорировать нельзя.
- Перед resolve вызывается config; наблюдались многосекундные задержки, кэширование конфигурации как оптимизация не реализовано. Свежесть разрешений нельзя подменять подсказкой UI.
- Диагностика зависит от свежего lease и может не записать часть события при сетевой проблеме. Проверять это при расследовании, не открывая полный экспорт всем пользователям.
- Звонки отложены по просьбе пользователя. Не требовать их как обязательный текущий шаг.

## 6. Какая версия была стабильной до защиты

**Точного номера последней полностью стабильной версии непосредственно перед защитой я достоверно назвать не могу.** Пользователь сообщает о хорошей работе перед этими изменениями; его наблюдение нельзя обесценивать. Но связка этого наблюдения с конкретным APK не закреплена полной приёмкой в доступных документах.

- **0.3.33** — последняя техническая версия перед безопасностью, GitHub-коммит **`530becbfa2b7c0f8c4bce2b840e7baa779b13336`**. Следующий security-коммит 0.3.34: **`296f0a43c3bd5d1ca7fc805ed26f2a458c6b890a`**. Это правильная граница для сравнения, но не доказанно бездефектная версия для обещания пользователю.
- **0.3.23** — есть явное подтверждение владельца, что воспроизведение работает хорошо, и документ `docs/android/OWNER-CHECK-2026-10-21.md`. В наблюдённом run отработало возобновление наушников без нового seek и естественное завершение. Позже добавлено много функций/исправлений; этот один успешный run не сертифицирует все условия и не является автоматическим основанием откатывать на неё публичную защиту.
- **0.3.43** — последний кандидат, только автоматическая проверка. Успешного пользовательского результата после его выдачи нет.

Не писать новому пользователю «0.3.33 точно была идеальна» и не выдавать 0.3.23/0.3.33 как новое защищённое приложение без аудита их ограничений. Старые APK могут содержать архив исходников и доступную всем диагностику. Сравнение с ними — исследование, а не разрешение вернуть эти свойства.

## 7. Соответствие исходников и готового APK

До 0.3.42 проверялось совпадение `classes2.dex` в APK с промежуточным DEX. На случае 0.3.41 выяснилось: **совпадение двух промежуточных/готовых файлов не доказывает наличие обещанной правки**. Предыдущие заявления о «проверенной сборке» были недостаточными.

Текущая проверка:

1. Свежий уникальный work-dir, проверка SHA исходных Java до/после compile/tests/packaging; изменение исходников во время работы обрывает выпуск.
2. Компиляция реального addon и host-тесты. `TestPure` проверяет записанную пару исполнителей после записи/чтения IdentityCache, используя реально скомпилированный addon. `TestHandoverClock` проверяет идентификацию, переход, отмену, записанные расхождения; остальные suites — хвост, pause/resume, сеть, Range, старые callback, 300 переходов и виртуальный длительный run.
3. Проверки подписи, zipalign, package/version/API, manifest, неизменности исходного каталога/компонентов/разрешений, отсутствия секретов/архивов исходников и совпадения встроенного DEX.
4. **Независимая декомпиляция уже подписанного APK**: наличие `AlbumMatch.artistKey`, вызовы этого метода из `match` для обоих входов; наличие handover guard; версия addon; в 0.3.43 значение350 мс и его использование в fade-коде.
5. Квитанция с SHA256 APK, DEX, сертификата и `source_fingerprint`. В runtime-заголовке с 0.3.42 есть `matcherRevision: 2`.

Ограничение: это набор контролей конкретных дефектов, не формальное доказательство эквивалентности каждого исходника всему APK, не независимый pentest и не проверка реального звука. Расширять смысл зелёных полей нельзя.

## 8. Что категорически нельзя менять в этой задаче

- **Компьютерное расширение**, его исходники/сборки, `feature/api-range`, desktop-сессии. Не делать откат общей ветки ради телефона.
- **Общий backend, API-контракты, авторизацию, refresh rotation, права, каталог, БД, аудиофайлы, хранилище и production deployment**. Не выполнять ремонтные POST/SSH/миграции как часть этой Android-работы.
- Сайт CELIKOM, CMS, `website/**`, независимый `ad-protection/**`, корневые конфигурации/зависимости и workflows. Разрешённая область — **только `android/**` и `docs/android/**`**. Не переписывать guard ради обхода ограничения.
- Не сливать всю Android-ветку в desktop: Android-ветка содержит намеренные удаления унаследованных workflow. Единственный Android workflow — проверка изоляции; она не собирает/не деплоит APK и не использует production secrets.
- Package `pro.celikom.nativeprobe`, ключ подписи, сохранённую сессию/installation_id нельзя менять ради эксперимента. Не предлагать удаление приложения/данных как обычное исправление.
- Не возвращать публичный экспорт полной диагностики, `legacy_tools`, исходники в APK; не считать промокод достаточным признаком администратора. Не доверять произвольному broadcast для подключения эффекта.
- Не менять глобальную громкость телефона, не оставлять Яндекс заглушённым при Stop/ошибке. Не игнорировать реальный seek/паузу ради маскировки лагов. Не проигрывать старый callback для новой песни.
- Не менять утверждённые записи каталога/демо AU/музыкальные файлы, чтобы «подогнать» мобильный тест.
- Не отключать проверки подписи/готового APK и не переименовывать старый APK в новый релиз. Новые runtime-изменения требуют новой сборки с возрастающим versionCode.

Новые изменения за пределами этого контура требуют отдельной явной задачи пользователя, а не расширения текущего ремонта.

## 10. С чего продолжать

1. Подтвердить GitHub HEAD и исходники Android, прочитать последний отчёт целиком по runs; проверить доступные готовые APK по хешам. Не начинать с очередного изменения таймаута.
2. Использовать границу 0.3.33→0.3.34 для полного сравнения окружения: сервис, аудиосессии, auth/очереди, журнал, launcher, упаковка. Сохранить отдельно подтверждённые факты и гипотезы.
3. Рассматривать последнее изменение 0.3.43 как непринятый кандидат. Не заявлять, что весь процесс стабилен, потому что конкретный цикл перестал воспроизводиться на host.
4. Если понадобится откат поведения — переносить понятные ограниченные изменения в Android-кандидат с тем же package/ключом и новым versionCode. Не откатывать общий сервер или компьютер и не возвращать открытые приватные инструменты.
5. До выдачи следующего APK проверить всю цепочку: определение ID → resolve → подготовка → seek → начало decoder clock → переход → seek/пауза/Next/конец/ошибка → восстановление оригинала, включая реальные профили задержек из файлов. По возможности проверить физический Android, если такие средства доступны; сейчас такого замера не было.
6. Отправлять пользователю конкретный результат с краткими фактами и оставшимися пределами. Не заставлять его собирать диагностику за рулём. Никакой новый APK в рамках подготовки этого документа не создавался.
