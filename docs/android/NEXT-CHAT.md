## Почему сменили подход

В реальном журнале `CELIKOM-combined-20261029-140931.txt` (есть запуск 0.3.47 с `2026-10-29T14:01:27+03:00`) видны:

1. Перемотка 469.245s -> `replacement_resume_fast` 469.283s (retained effect) -> `replacement_original_restored` 469.772s -> seek complete 469.931s -> original muted AGAIN 469.970s. Вышедший из паузы decoder был затронут старым delayed callback. Отдельный `transition` не гарантировал отмену при seek.
2. В старом коде на midpoint перехода `originalMix≈0.5` и `player.volume≈0.5` одновременно: два источника реально смешивались алгоритмом.
3. Host-тесты прежних выпусков проверяли, что каждый механизм формально работает, но не инвариант «второй трек не слышен одновременно с первым».
4. Нельзя списывать все слышимые reconnect на сетевой HTTP; нужно отделять `replacement_recovery`, `media3_connected`, старую нативную медиасессию, `source_discontinuity`.

**Что изменено в 0.3.48:**

- Добавлен `AudioOwnership.java` со состояниями, выдачей только эксклюзивного audio grant, уникальной lease для паузы.
- Fade теперь **break-before-make**: после проверки декодера и sync полностью приглушает оригинал (-100 dB) **до** роста громкости подмены. Обратно вторичный плеер сначала замолкает, только затем исходный становится слышен. Это может дать небольшой период тишины, но устраняет *намеренную* одновременную слышимость двух записей.
- При возобновлении `audioOwner.cancelPause()` отменяет старый таймер, проверяются актуальные `player`, `effect`, lease, seeking, identity/source.
- При buffer wait сначала вторичный плеер получает ноль и паузу; только потом восстанавливается оригинал.
- При повторном подключении DynamicsProcessing к *уже работающему* secondary нельзя включить его на полную без gated fade.
- Сохранены: 0.3.46 duration gate 500 мс, 0.3.47 короткая пауза 1000 мс/аварийная 350 мс, допуск Bluetooth/sync 350 мс, проигрывание next-track, auth/report и UI.

**Автоматические проверки в предыдущей сессии:** PASS для реального движка с fake Android, старых и новых тестов (113 engine, 53 phone replay, 39 resume, 604 long-run включая 300 смен/15 виртуальных часов, 43 car, 51 progressive stream, 40 clock/matcher, 28 обязательных ownership); полный набор остальных `addon/Test*.java`; независимое декодирование и проверка подписанного APK. Код Java в GitHub соответствует исходникам сборки по точным Git blob SHA, включая `ReplacementEngine.java`, `AudioOwnership.java`, `AppVersion.java`; runner и verifier также выровнены. Готовый подписанный файл — `CELIKOM_Android_0348_CANDIDATE.apk`. SHA256 `3e8c00d7e11c471fce9dbc811af96f5ec559d97b9e18c644456580ecaddca62e`, 8,677,449 байт; versionName `0.3.48`, versionCode `49`. ## Среда сборки/подпись

В предыдущей сессии SDK+Deps+apktool были восстановлены отдельно, и локальная сборка возможна. Нельзя полагаться на пути старого рабочего контейнера в новой сессии. Формат команды:

```bash
python3 android/native-companion/build_release.py \
  --sdk /PATH/TO/sdk \
  --build-tools /PATH/TO/sdk/build-tools/android-16 \
  --apktool /PATH/TO/apktool-2.11.1.jar \
  --base-apk /PATH/TO/CELIKOM-0.3.22-install.apk \
  --signing-dir /PRIVATE/SIGNING-DIR \
  --output /PATH/TO/CELIKOM_Android_0348_CANDIDATE.apk
```

Точные SHA: `android/native-companion/build-inputs.json` и `docs/android/RELEASE-0.3.48.json`. Private signing **не коммитить**, не печатать и не передавать пользователю в комплекте. Key rotation неприемлема для установки поверх прошлой версии. GitHub isolation Actions не компилирует APK и не подтверждает звук.
