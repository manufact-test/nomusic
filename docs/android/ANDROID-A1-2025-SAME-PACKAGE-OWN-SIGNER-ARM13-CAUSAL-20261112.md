# CELIKOM Android A1 — каузальный тест исходного имени пакета с нашей подписью (12.11.2026)

**Статус:** Stage A **NO-GO**, Stage B **LOCKED**. Это отчёт об изолированной диагностике, **не** выпуск APK. Текущая исследовательская ветка: `experiment/android-a1-2025-causal-startup-controls-20261112`.

## Зачем понадобился ещё один контролируемый эксперимент

До этого реальный CI подтвердил: исходный 2025 GPR issuer-signed комплект 16/16 APK работал 75 секунд [CI 43091414430](https://github.com/manufact-test/nomusic/actions/runs/43091414430). Наш независимо подписанный, отдельно названный CELIKOM-клон **все 16 APK подписывает и устанавливает**, но основной процесс падает с `JAVA_CRASH / APPLICATION_STATE`, [CI 43106889245](https://github.com/manufact-test/nomusic/actions/runs/43106889245).

Оставалась неразделённая гипотеза: падение вызвано заменой идентификатора пакета `ru.yandex.music` на `pro.celikom.yandex.nativeclonelab`, либо новым преобразованием ресурсов APKEditor/ARSCLib, либо сторонней подписью/перепаковкой. Вместо ещё одного повтора клона проведён отдельный **дифференциальный контроль без переименования и без APKEditor**.

## Что реально сделал тест

В одноразовом чистом ARM64+ARMv7 Android13 Redroid, не на телефоне владельца:

- Оригинальный XAPK 2025.10.4 #120.1gpr 45 961 661 байт, SHA256 `8e43be8900d28ee92c8e315ed07069568858bfd4a593757fba9d276bd0c54053` получен только из ранее загруженного **неопубликованного** GitHub draft Release. Прежде чем что-либо делать, 16/16 издательских APK криптографически проверены.
- Временная лабораторная копия сделана **без замены имени пакета**, без изменения манифеста, resources.arsc, DEX и .so, без APKEditor/Apktool, LSPatch и чужого модуля. ZIP переупакован в собственные промежуточные файлы; старые v1/JAR signature entries отброшены в одноразовых lab-файлах.
- Все 16 подписаны **собственным одноразовым ключом** (отличным от издателя), а затем проверены обязательным apksigner с унаследованным от original base.apk minSdk=24. Издательская подпись НЕ подделывалась, в Android security, Passport, DRM и Play Protect проверки НЕ вмешивались.
- В чистой ARM13 гостевой среде установлены 16 частей как **`ru.yandex.music`** (без параллельной установки оригинала: цель только разделить причины, это не предлагаемый продукт). Запущена исходная нативная MainScreenActivity; затем строгие 25 проверок за 75 секунд.
- Не логировали исключения целиком, приложение, имена внутренних классов, PID, пути, токены или учетные данные. Только ограниченные результаты Android ApplicationExitInfo и разрешённые категории приватного crash-buffer. Бинарных артефактов GitHub Actions/Release не создано, всё удалено после завершения CI.

## Технический вывод и предел доказательства

- **Замена package name НЕ является необходимым условием наблюдаемого `APPLICATION_STATE` падения.** Приложение упало даже при неизменённом оригинальном package name.
- **APKEditor/ARSCLib rebuild НЕ является необходимым условием этого падения.** Контроль полностью исключил его, при сохранённых манифесте/ресурсах/payload.
- Остаётся общий набор отличий от успешного оригинала: **собственный сертификат вместо издательского и неизбежная перепаковка ZIP/signature metadata**. Этот эксперимент **НЕ доказывает**, что причина именно проверка сертификата в Java или DRM. Издательская подпись — также право/договорное ограничение, а не просто технический параметр. Никакого утверждения, что vendor trust «обойдён», нет.
- Повторять переподпись, APKEditor или изменение package name без новой независимой причины **бесполезно**. Конкретную внутреннюю инструкцию/проверку Яндекса нельзя объявлять найденной по одной категории `IllegalStateException`.
- Ресурсы, DEX и manifest не были **преобразованы** в этом контроле, но ZIP-структура и signature metadata отличаются: нельзя утверждать побайтовую идентичность всего APK или полную каузальную изоляцию только подписи. Равно нельзя приравнивать удачную установку к устойчивому native UI.

## Допустимые следующие действия

1. Только явно законный, безобходный анализ подписных permission/Android package-integrity контрактов как объяснение ограничения. Если для работающего нативного стороннего UI необходима подпись/лицензия издателя — **зафиксировать внешний blocker**, не выполнять self-check bypass, sig spoof, DRM/Passport, отключение Play Protect, перенос LSPatch уровня 1/2 или чужого бинаря.
2. Для **одного отдельного CELIKOM APK** с полным нативным UI Яндекса нужны поддерживаемая интеграция и право на модификацию/дистрибуцию от правообладателя, если публичная архитектура не позволяет это законно. Подготовленные [официальные варианты и вопросы для правообладателя](ANDROID-A1-PUBLISHER-SUPPORTED-INTEGRATION-OPTIONS-20261111.md) уже есть. **Самостоятельно к Яндексу не обращаться** без разрешения владельца.
3. После независимого подтверждения законного стабильного UI запускать штатную авторизацию, библиотеку/Мою волну, подключать уже принятый issue #42 / PR #43 source-selection, проверять единый декодер и реальный звук. Готового пользовательского APK пока нет. После фактического звукового одобрения владельца Stage A отдельно напомнить о Stage B — замене LSPatch собственным механизмом.

**Не трогали:** замороженная основная A1 `cc4cb0f93489168db21502f3ef195855ae9fb743`, Test.50, Windows, расширение, backend/API, админка, production, оригинальный черновик Release, HONOR владельца. Issue #41 должен оставаться OPEN.
