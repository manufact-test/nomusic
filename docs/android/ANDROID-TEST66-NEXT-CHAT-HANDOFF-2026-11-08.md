## Что реально было и почему правили

В Test.64 / Test.65 в шторке сверху уже было название трека из Media3, а снизу могло бесконечно висеть «Определяем песню». Название/исполнитель/длительность из Media3 **не равны достоверному Yandex Track ID**. В предыдущих логах «ИСКАЛА» (Земфира) и «Гармония» (ARTIK & ASTI) публичный альбомный API Яндекса возвращал **HTTP 451**. Истинный Track ID не нашёлся, но кэш одобренных замен CELIKOM уже был свежий, полный, **133 строки** для того прогона. На Test.65 интерфейс ошибочно привязывал отображение результата к точному ID.

Test.66 исправляет **только слой статусов**: `AlbumProbe` сохраняет `publishedOwn` — точный результат совпадения с *актуальным, только approved* каталогом; `PlaybackUi` передаёт `catalogueFresh/catalogueStatus`; `AppPresentation` / `NotificationState` сразу показывают «Версия есть в каталоге CELIKOM», «В одобренном каталоге CELIKOM версия не найдена», неоднозначность либо «Проверяем наличие версии CELIKOM». Название песни показывается независимо от найденного ID. **Никаких выводов о модерации**: в snapshot отсутствуют pending-заявки; даже `NO_MATCH` означает только «нет совпадения среди approved». Запрет подачи песни без доказанного ID сохраняется. **Новый диагностический event** `notification_status_published` содержит *реально отправленный Android текст*.

## Обязательный первый проход по новой диагностике

1. Определить в файле точные границы запусков (`run_start`, `version`) — combined содержит предыдущие версии, их нельзя усреднять с Test.66. Убедиться, что **последний запуск действительно `0.3.85-test.66`**.
2. Для каждого проблемного трека собрать таймлайн `album_observation` → `hybrid_identity` (`ownCatalogue.status`, `catalogueFreshComplete`, `decision.reason`) → `album_request/album_response` → `replacement_resolve` → `notification_status_published` и, если есть, presence/upload-status. Отдельно отметить, **была ли версия approved в локальном каталоге** и был ли подлинный ответ сервера. Не выдавать имя трека за Track ID.
3. Проверить шторку и экран приложения при 451, `NO_MATCH`, `UNIQUE_METADATA_CANDIDATE`, `AMBIGUOUS`, паузе/Next и возврате после отключения сети. Сверить текст, реально опубликованный в шторку, с состоянием, а не только прохождение Java-тестов.
4. Замерить **неравномерную задержку**: на каждой песне время `album_observation` → подтверждённый `replacement_resolve` → `replacement_prepared` → `replacement_transition_complete`; отделять сетевой альбомный lookup, current resolve, скачивание/кэш, подготовку декодера и ожидание синхронизации. В старом Test.65 были ≈1,90 с «Новогодняя» и ≈1,57 с «Скажи», при многих более быстрых включениях — это не гарантия тех же цифр в Test.66.
5. Отдельными открытыми кейсами оставить **RASKOL ID 42884423** (паузу/перемотку официальная Media3-сессия не всегда передаёт), **«Дым» ID 39949113** (BUFFERING), реальные акустические переходы и настоящий ID из открытого Android Media3. Test.66 их **не исправляла**; если диагностика не проверяет кейс, прямо написать «не проверено».

## Границы изменений

- **Не менять** stable Android `0.3.92`, эталонное поведение звука Test.50, main, production OTA, Hostinger/backend, компьютерное расширение или параллельные Android/desktop/Blur ветки. Test.66 — экспериментальная, отдельная от stable.
- Сначала анализ новой диагностики и короткий фактический отчёт владельцу; потом **один связанный блок** исправлений при подтверждённой причине, в новой Android-only ветке от нужного тестового baseline. Не «чинить полпроекта» ради одного статуса. Не заявлять улучшение звука по CI.
- После кода: полная Android host-регрессия, D8, side-by-side подписанная APK, сверка подписи/SHA, **сохранить APK в ChatGPT Library `/CELIKOM/Android/Test`** вместе с verification и receipt, обновить этот handoff / `NEXT-CHAT.md`, дать пользователю только понятные результаты и что проверить на HONOR.
- Если данных не хватает для безопасной правки — прямо обозначить, чего именно не видно в новой диагностике. Никаких придуманных `found:false`, «на модерации» и подтверждений исправления на телефоне.
