## Confirmed architecture (source code)
`android/native-companion/addon/src/pro/celikom/nativeprobe/identitydiag/ReplacementEngine.java`: owns a **separate `android.media.MediaPlayer player`** for CELIKOM audio (main decoder around line 1221; speculative decoders too). Original Yandex audio session is attenuated via `DynamicsProcessing` audio effect. `ProbeService` observes Yandex's *remote* `androidx.media3.session.MediaController` and constructs `PlaybackSource` from reported media item, playback state and interpolated position. Every Yandex native seek/pause needs a separate transport/decoder response by CELIKOM. `replacement_hot_cached_seek_ack` only proves our decoder's own seek callback. **This is literally a two-player architecture, not just a cosmetic UI bug.**

Per official Android API, `DynamicsProcessing` is an effect acting on an audio session (gain/EQ/compressor/limiter); it does not inject a completely different audio file or transfer Yandex's internal decoder control to CELIKOM: https://developer.android.com/reference/android/media/audiofx/DynamicsProcessing. A custom real in-place audio pipeline would require a separately **proven** integration path compatible with official unmodified Yandex, no privileged permissions or root. Merely assigning the same session ID to another AudioTrack is not proof of one playback clock or shared Yandex pause/seek.

## Architectural hypothesis vs proof
**Observed:** Different Yandex externally published event behavior during same-item seek: control tracks send transient buffering/isPlaying callbacks, RASKOL and «Дым» only jump position. Separate CELIKOM player depends on these partial/stale external observations, so status and audible control can diverge. Prior Test.68/69 failures confirm the remote session can become stale or frozen after experimental external commands. **Not proven:** internal Yandex decoder/caching/format/DRM reasons; exact acoustic latency; an alternative permissionless source that provides reliable per-track pause/seek on HONOR.

Do not claim «network not involved»: both fresh problem-track seeks occurred before full download. But previous Test.67 experiments showed trouble even with warm/cached replacement, so download speed is **not a complete explanation**.
