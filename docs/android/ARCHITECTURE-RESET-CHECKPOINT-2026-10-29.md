## 5. Смена способа разработки: архитектура, а не новый таймер

Текущий код: `ReplacementEngine.java` самостоятельно держит MediaPlayer, DynamicsProcessing, stream, async seek, fade, pause lease, error recovery и retry; `ProbeService.java` получает независимые Media3 callbacks и делает sample раз в 250 мс; `AudioOwnership.java` уже описывает условную эксклюзивность, но не управляет **всем жизненным циклом**. `SyncPolicy.java` разрешает дрейф до 1.5с. Нет атомарной смены аудио у двух независимых процессов. Эту фундаментальную границу Android/Яндекса нельзя скрыть настройкой задержки.

**Первый этап нового чата — спроектировать и реализовать согласованную state machine** для Android audio handoff, сохраняя API, UI и сервер без изменений:
- Явные состояния: `SOURCE_ONLY` (без attenuation), `PREPARING`, `ALIGNING` (secondary без звука), `REPLACEMENT` (исходный звук приглушён и decoder подтверждён), `PAUSED`, `RECOVERING`, `TRACK_UNSUPPORTED` (причина конкретного трека), `STOPPED`; окончательный набор может быть уточнён при рефакторинге.
- Единая очередь событий/согласованный контроллер: новая identity/alias, play/pause, seek, source buffering/end, decoder prepared/seek-complete/completion, effect control loss, route change, network/audio stalled, user stop. Устаревшие события блокируются generation/track key и валидным текущим снимком. Не смешивать сообщения о старом треке с текущим.
- Центральные **инварианты**: только одна сторона имеет право на ненулевой программный output; перед освобождением original attenuation secondary ставится в mute/pause; при любой ошибке оригинал восстановлен (fail-open); старый декодер никогда не играет после смены source identity; нет перезапуска старого трека от позднего callback; никакой таймер не получает право звука без проверки поколения.
- Разделить **track matching/duration policy** и **transport/audio ownership**. Неверная длительность (500 мс) — законченный статус текущего трека, объяснимый пользователю, а не попытка «ускорить» аудио.
- Развести типы drift: реальный seek, виртуальная позиция Media3, задержка getCurrentPosition secondary, устойчивый hardware/Bluetooth offset, акустическая задержка вывода. При длительной нестабильности — безопасное восстановление оригинала, а не серия слышимых seek/fade. Зелёный host-контроль != измерение output.
- Явно описать конец песни/переход: отключить старый secondary **до** разрешения новому звуку, не делать предположений, что нулевая позиция старого alias всегда означает переход. События должны быть подтверждены по текущей identity и транспортному состоянию.
- Логи и UI отражают фактические права на вывод и причины отказа; «замена активна» не показывать, если играет только original.
- Сохранить рабочее поведение пауз/seek, строгий exact/album matching и security boundary.

**Порядок реализации:** (1) сформулировать контракт состояний/событий/инвариантов и красные тесты из прикреплённого журнала; (2) изменить код одной согласованной серией, убрать дублирующие конкурирующие переходы; (3) весь host suite + независимые release/isolation checks; (4) инструментация на реальном Android/маршрутах настолько, насколько это доступно, с честной оговоркой о непроверенной акустике; (5) ТОЛЬКО ЗАТЕМ — одна новая версия APK на старом сертификате и объединённая пользовательская проверка. Не делать новый APK между пунктами (1)–(4).
