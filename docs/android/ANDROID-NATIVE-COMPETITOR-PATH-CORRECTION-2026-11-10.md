## Что подтверждено публичным источником

[Desai0/ChromaSync-Mobile — README](https://github.com/Desai0/ChromaSync-Mobile) (проверено 10.11.2026, в публичном репозитории только README):

- Android-решение работает как **модуль внутри совместимой версии нативной Яндекс Музыки**, по заявлению автора заменяя аудиодорожки, сохраняя штатные очереди/UI.
- **Без root**: требуется совместимый исходный Yandex APK, отдельный ChromaSync APK/модуль и патчер, который **подготавливает целевое приложение на устройстве**. При переходе с официальной установки может потребоваться её удаление из-за несовпадения подписи; данные/загрузки могут быть потеряны.
- **С root**: LSPosed с modern API, модуль включается для соответствующей версии Яндекса.
- Модуль использует локальную подготовку и кэш: первое воспроизведение может остаться оригинальным при неготовом источнике. Это конкретная UX-политика конкурента, не доказательство безошибочной pre-prepare подмены.
- Автор прямо пишет, что проект независим, не одобрен Яндексом. **Никакого официального партнёрского SDK он не требует** в опубликованной инструкции.
- **В публичном Android-репозитории нет исходного кода модуля**, поэтому нельзя честно назвать его decoder hook/конкретный метод подмены, не исследовав законно доступное поведение. README ≠ рабочая спецификация.

## Что поменять в нашей инженерной стратегии

1. **Отменить неверный критерий «только официальный партнёрский API».** У конкурентов есть подтверждённая по инструкции практика отдельного подготовленного нативного клиента, а не второго проигрывателя. Это практическая гипотеза; технические особенности и действительная надёжность не верифицированы нашей командой.
2. **Не путать три разных вещи:** (a) нетронутый оригинальный APK на HONOR; (b) параллельный другой-package clone, который в прежнем CI завершает MAIN `EXIT_SELF(0)`; (c) подготовленный патчером совместимый нативный APK с прежним package name и новой подписью. Отказ в (b) **не доказывает провал (c)**. Но (c) не ставится поверх официального с другой подписью без предусмотренного Android изменения установки: основной HONOR запрещено трогать.
3. При наличии **отдельного разрешённого ARM-устройства** исследовать совместимый rootless in-process сценарий на ОДНОМ тестовом клиенте, без параллельного clone package ID. Не повторять x86/ARM translator и AppMetrica DEX-патч. Не обходить Play Protect, DRM, авторизацию или проверку подписей. Ничего не устанавливать на HONOR без отдельного разрешения.
4. Начальные gates: нормальный запуск UI и вход **только в родном Яндексе**; read-only доказательство точной активной `trackId + edition + playback generation`; действительный native descriptor до prepare; только потом подключать готовый `NativePrePrepareAdmission` и проверять единственный источник. Никакого второго MediaPlayer, WebView или пароля CELIKOM от Яндекса.
5. До выполнения gates не выпускать APK. При отсутствии дополнительного ARM-устройства не симулировать настоящий опыт на x86 и не выдавать synthetic green CI за подмену. Проблемы «Раскол», «Дым», первый «пшик», Next/радио тестировать только после реальной native интеграции.
6. **Сохранить доказательства:** в собственном ARM witness на HONOR ранее подтверждён hook в **своём** приложении; он не доказывает hook в Яндексе. Clone `EXIT_SELF(0)` — именно отказ другой-package архитектуры, реальный вызывающий код неизвестен. Test.50 сохраняется неизменным.

## Ограничения и конкретное действие

Не посылать письма Яндексу. Не переделывать на отдельный player и не обращаться к неофициальному аккаунтному API. Следующий технический этап — подготовка строго изолированного ARM-native compatibility preflight на *запасном устройстве*, затем один ручной тест после подтверждения безопасной установки. Не пытаться обходить Android-подпись или издательские защитные механизмы для установки.

**Статус:** обоснованная стратегия, НЕ проверенная нативная подмена и НЕ разрешение на установку. Этот коммит — только корректировка документации; нового CI/audio теста нет. Test.50, официальный HONOR, Windows, extension, server, DB, production не тронуты.
