# CELIKOM Android — единая передача на разработку после исследования сторонних проектов (08.11.2026)

## Решение владельца и обязательный принцип
Владелец потребовал: **не выпускать APK на догадках**. Следующий чат должен сам выполнить **один большой законченный инженерный блок**: исследовать источники идентичности и надёжности сигналов официальной Яндекс.Музыки → проверить по коду и диагностике → внести доказанные безопасные изменения → прогнать регрессию → **один** подписанный экспериментальный APK только при существенном улучшении. Не дробить на серию фиктивных Test.64/65/66. Если API не даёт достоверного сигнала, документировать границу возможностей и не маскировать таймерами. Не требовать у владельца снова пересказывать историю.

## Фактическая диагностика (не путать с гипотезами)

- Test.62 live approved replacement catalogue HTTP200 / **133** строки. Test.61 HTTP200 / 130, Test.60 — старый CDN 404. Не изобретать новую ручную синхронизацию.

Текущий track `123250095`: next prefetch `106618982` стартовал на 66ms, а current resolve ~200ms, cold start ~201ms: доказан **порядок** операций, но не доказана причина слышимого дефекта. В файле RASKOL `42884423` подмена прошла, но нажатия UI работают не всегда; это разные факты.

CELIKOM локальную перемотку после доставки нового положения делает быстро, то есть простой таймер не решает отсутствие сигнала.
- **Лёша Свик — «Дым» / Track ID 39949113**: официальный источник остаётся `BUFFERING`, `playWhenReady=true`, `isPlaying=false`; watchdog с принудительным освобождением Media3 контроллера в Test.58 усугублял ситуацию повторными `SecurityException`. ## Важная настоящая точка для Track ID
Текущий `ProbeService.connect()` напрямую подключается к `com.yandex.music.shared.media.session.session.Media3LibraryService` через Media3 `SessionToken`; `MediaItem.mediaId` из текущих логов — короткий alias (9, 10, 55), **НЕ авторитетный Track ID**.
- Провести *read-only, ограниченную и privacy-safe* инвентаризацию **фактически предоставляемых** `MediaItem`, `MediaMetadata`, `MediaMetadata.extras`, `RequestMetadata`, `mediaUri`, `localConfiguration`, `currentTimeline` / `Timeline.Window` и `MediaSession` commands/extras (только публично доступные поля). В diagnostic логировать только названия ключей, типы, признаки и числовые ID, без токенов/URL с подписью/секретов, без персональных данных; явно проверять реально ли это Track ID, сопоставлять с album API и последующими seek/next.
- Важно: прочитывание этих дополнительных объектов из *чужой* сессии **может не работать**; не обещать, что Yandex публикует Track ID или свежий pause callback.
- `ProbeService.connectLegacyPosition()` уже пытается пассивный `android.media.browse.MediaBrowser` с тем же сервисом, `legacy_position_source_unavailable browser_connect` на телефоне. Разобраться с API и экспортируемыми компонентами/разрешениями, но **не добавлять вторую конкурирующую Media3 сессию, root, Accessibility, Notification Listener или перехват приватного трафика**.
- Existing fallback: `AlbumMatch.albumId(cover)` извлекает album id из `avatars.yandex.net`; `AlbumProbe` загружает `/albums/{albumId}/with-tracks`; `HybridIdentity` требует точный title/artist/duration и умеет current approved catalogue / learned catalogue. Сначала выяснить ложные отказы, 451, edition conflict, связь с Track ID; расширять только при детерминированных критериях. Metadata match **не является доказательством конкретной версии**, особенно одинаковых треков в нескольких релизах.
- Проверить пользу явного `track ID` на server `resolve` и `replacement-catalog` для безопасности/скорости, только при подтверждённом источнике идентичности.

## Исходники конкурентов (анализировать код, а не названия)
1. https://github.com/Hazzz895/FckCensor — `src/api/main-api.ts` `buildPlayerReplacement(trackId)`, `sourcesCollection.firstAsync`: источник подмены по точному trackId, внутренний SDK bridge. Переносима архитектура приоритетов провайдеров/подтверждений идентичности, **не** чтение Android UI.
2. https://github.com/S4YN3X/FkCensor — `assets/inject.js` разбор `list_v2.json` с trackId→audioURL, перехват внутренних network/renderer ответов. Переносима идея однозначной индексированной таблицы approved; нельзя напрямую внедрять десктопный injection в официальный Android.
3. https://github.com/mrvokintos/YandexMusicMod — `src/mod/features/ym-liberty/ym-liberty.ts` `getLocalFileDownloadInfo(trackId)` переопределяет получение URL внутри десктопного клиента. Прямой перенос невозможен без изменения официального приложения, что запрещено.
4. https://github.com/gagayhhad-tech/ym-liberty-android — `android_app/assets/www/app.js` `streamCache: Map<id, Promise>`, `preloadNextTrack()`, dedicated preload audio element, checked current next ID, crossfade. Переносимы **single-flight requests, cancel/invalidate stale next, priority current, bounded next cache**, но не собственный WebAudio плеер.
5. https://github.com/aeviww/yandex-music-client — `desktop/src/lib/audio.ts` `warmNext(url)`, `clearWarm()`, `sourceToken`, `isCurrentToken()`, handling `AbortError`. Переносимы **generational operation invalidation, safe cancellation, bounded prewarm**, не собственный плеер. В CELIKOM уже есть `generation`, `audioOwner.ticket`, `lookaheadPrefetchGeneration`: сравнить перед добавлением.
- Честная оценка: из конкурентов **в Test.63 реально не перенесено ни одной технологии**. Вся работа должна опираться на diff и воспроизводимые регрессии.

## Что не доказано и нельзя утверждать
- Test.63 не доказывает ускорение; GitHub PASS доказывает build/tests, не физическое воспроизведение и не исправление слышимых щелчков.
- `MediaItem.mediaId` не доказан как Yandex Track ID, наоборот наблюдаемые aliases это не track IDs.
- Наличие `MediaMetadata.extras` как типа в Android API не доказывает, что Yandex положил туда что-то полезное.
- Обычный `Media3.getCurrentPosition` может иметь локальную интерполяцию, не является подтверждением UI seek.
- Ни один конкурент не доказал доступ к чужому официальному Android-плееру, поскольку их условия работы другие.
