# CELIKOM Android — исследование реальной причины, TEST.58 evidence-only, 2026-11-08

**Статус:** пользователь отверг прежний подход: серии Test.51–57 не исправили отсутствие управления Pause/Seek у RASKOL / «Дым», появились регрессии у хороших песен. Нельзя делать новую «починку» без надёжного сигнала. Test.58 — первая **диагностическая**, а НЕ «всё починено», сборка из точной принятой Test.50.

## Источники и факты
1. [AndroidX Media3 MediaUtils.java](https://github.com/androidx/media/blob/release/libraries/session/src/main/java/androidx/media3/session/MediaUtils.java): функция `getUpdatedCurrentPositionMs` буквально делает `positionMs + (SystemClock.elapsedRealtime() - eventTimeMs)*speed`. **Следствие:** увеличивающаяся `MediaController.getCurrentPosition()` — локальная **оценка контроллера**, а НЕ доказательство, что Яндекс в данный момент воспроизводит трек, и НЕ подтверждение нового состояния из Yandex UI. Предыдущие выводы «Яндекс точно играет внизу без звука» были чрезмерными.
2. [Google Player.Listener](https://developer.android.com/reference/androidx/media3/common/Player.Listener) и [Player events](https://developer.android.com/media/media3/exoplayer/listening-to-player-events): только фактический полученный `onEvents`, `onPlayWhenReadyChanged`, `onIsPlayingChanged`, `onPlaybackStateChanged` и `onPositionDiscontinuity` подтверждают получение нового состояния от публичной сессии. Сам факт callback не гарантирует согласованность с внутренним UI Яндекса.
3. [AndroidX media issue #3248](https://github.com/androidx/media/issues/3248): воспроизводимый баг на API33/Media3 1.10.1 — ложный `onMediaItemTransition` после seek/изменения плейлиста; разработчики подтвердили проблему и предложили фикс. **Это сходный дефект, не доказательство одинаковой первопричины RASKOL/«Дым».** Нельзя вслепую трактовать каждый transition callback как смену фактической композиции.
4. [SessionToken](https://developer.android.com/reference/androidx/media3/session/SessionToken): публичные `getConnectedToken` и `SessionToken.getAllServiceTokens` позволяют **без отправки команд** узнать фактическую подключённую сессию, версию библиотеки и перечень *объявленных* медиа-сервисов приложения Яндекс. **Объявленный сервис ещё не значит активный.** На Android 11+ нужен visibility query для нахождения других сервисов; пустой результат не доказывает отсутствие. Идея для проверки: возможно CELIKOM читает не тот Yandex session, что использует UI. Пока это только гипотеза.
5. [Android MediaSessionManager.getActiveSessions](https://developer.android.com/reference/android/media/session/MediaSessionManager): все активные чужие сессии нельзя перечислить без системного `MEDIA_CONTENT_CONTROL` или разрешённого `NotificationListenerService`. Владелец категорически отверг эти разрешения, не добавлять. [Android Visualizer](https://developer.android.com/reference/android/media/audiofx/Visualizer) для подтверждения фактического чужого PCM требует `RECORD_AUDIO` — также отвергнуто. Анонимный `AudioPlaybackCallback` ранее в Test.53 давал ложную блокировку рабочих песен.
6. Попытка `android.media.browse.MediaBrowser` к тому же Yandex service в предыдущих APK вернула `legacy_position_source_unavailable stage=browser_connect`. Запрещено выдавать это за доступный достоверный канал. Test.52 повторный Media3 controller Яндекс отверг `SecurityException`. Никакого нового второго подключения.

## Почему предыдущие версии не давали ответа
- `onEvents` до Test.58 молча обновлял возраст последнего события и вызывал `sample`, **не записывая конкретные типы событий**, позиции при реальном событии, доступные команды, идентичность подключённой сессии. Из-за этого невозможно отделить «Яндекс не уведомлял» от «мы пропустили событие».
- `playback_health` в log был подписан `sourcePositionMs`, хотя часть позиций считалась MediaController локально — неверная интерпретация. Никакого API, подтверждающего звук из динамика, в этом значении нет.
- Тюнинг задержек, вторые контроллеры, анонимные аудио-сессии и принудительные reconnect без этих фактов неизбежно приводят к ложным гипотезам.

## Дальнейшее решение по фактам — не гадать
- **Есть входящий raw Pause/Seek на проблемном треке, но state engine их не применяет:** минимальный fix в клиентской обработке этих конкретных событий, регрессионные тесты на рабочих треках.
- **Raw callbacks отсутствуют только на проблемных треках, но найден другой опубликованный сервис Yandex:** сначала сравнить роли сервисов и возможность единственного подключения к правильному источнику (без одновременных контроллеров, никаких новых permissions), затем изолированный fix от Test.50.
- **Raw callbacks отсутствуют и альтернативного доверенного канала нет:** техническая граница внешней интеграции. Честно объяснить владельцу, не подменять реальный UI pause приблизительными таймерами/числом плееров. Дальше требуется поддерживаемое со стороны Yandex API/исправление MediaSession; не делать «работает» из случайного совпадения.
- **Отдельно «Дым»:** STATE_BUFFERING расследовать как startup/transport дефект. Играющая подмена здесь не должна стартовать до подтверждённого READY. Test.57 one-shot seek0 не выполнялся; не повторять как будто проверен.

**Стабильную ветку, эталон, текущие серверы, VPN и миграцию не менять.** После миграции на новый MCP стек перенести этот документ, Test.58 исходники и результаты CI; не копировать Hostinger secrets в репозиторий.
