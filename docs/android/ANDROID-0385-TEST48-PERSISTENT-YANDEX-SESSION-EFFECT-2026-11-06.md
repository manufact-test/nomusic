# CELIKOM Test.48 — стабильная аудиосессия вместо пересоздания обработки при каждой песне

## Почему идём этим путём

Владельцу **не нужны отчёты о миллисекундах**; нужно, чтобы разные песни не звучали с непредсказуемыми «пшиками», обрывами и повторными подключениям. После Test.47 песни находятся, загрузка обычно работает, но одни и те же треки ведут себя по-разному при повторном запуске. Это похоже на проблему границы воспроизведения, а не отдельного MP3.

Последняя отдельная **тестовая** диагностика `CELIKOM-combined-20261106-141814.txt`, run Test.47 с JSONL-строки 4245. В ней **16 раз на одной и той же Yandex session `4577`** создавалась/подключалась обработка `DynamicsProcessing` после очередного `replacement_original_restored`/release. Эти события происходили даже для уже подготовленных локальных файлов. Видны успешные замены, но фактического PCM/выходного сигнала нет. **Гипотеза**: многократное освобождение и подключение нативного аудиоэффекта к одной и той же сессии может добавлять непостоянные щелчки/разрывы. Это не доказано как единственная причина.

Следующий файл `CELIKOM-combined-20261106-172111.txt` — **main 0.3.90**, а не Test. Его нельзя выдавать за отзыв по Test.47/48. Проблемные backend `found:false` — другая задача, не причина щелчков при уже найденной замене.

## Test.48 — один эксперимент, а не десятки правок таймеров

- Ответвление строго от source Test.47 `9c90a73fc87a0b9b12d6c4da66c98028b14073cc`, пакет `pro.celikom.nativeprobe.test`; номер Test.48/code86133, ПК и stable 0.3.92 не меняются.
- После подтверждённой смены трека: **сначала сделать старый decoder беззвучным, вернуть Yandex source gain к 0dB, затем кратко держать привязанный native DSP**. При следующей песне с тем же верифицированным source session и после прежней clock/auth/decoder gate повторно использовать этот DSP, без его пересоздания и повторной активации.
- Никогда не переносить effect на новую audio session, не переносить ненулевой decoder gain; при stop, потере эффекта/контроля, смене session, невозможности восстановления, ручном возврате оригинала — старое release/fail-open поведение. Если следующая песня не найдена, сохранённый DSP сам освобождается через ограниченное время, оригинал продолжает играть.
- **Не менять** задержки seek, алгоритм подбора Track ID, source sampling, crossfade, наличие прав. Test.33 golden; текущая Test.47 — сравнение на том же телефоне. Секреты/сервер/ПК не затрагиваются.
- Добавлен host regression на цепочку двух треков с одной source session, timeout без следующей песни, stop, смену session; существующие host suites должны пройти в исходном режиме (эксперимент по умолчанию выключен вне изолированного Test-сервиса).

## Приёмка владельца

Один обычный проход, без анализа журналов в отчёте: 10–15 минут привычной музыки, вручную Next и возврат к уже звучавшему треку. Ответить только: **«пшиков стало меньше / так же / хуже»**, не пропадает ли замена, нет ли двойного аудио. Диагностику можно приложить одним combined TXT, если всё ещё слышны проблемы. После негативного результата вернуть Test.47; stable не трогать.

## Дальше, если щелчки останутся

Перестать бесконечно перебирать длительность fade. Рассмотреть архитектуру **одного непрерывного DSP/decoder аудиотракта** с объективным capture/loopback лишь при доступном добровольном, допустимом Android API, но не требовать у всех пользователей Accessibility, Notification Listener, микрофон или постоянный MediaProjection. Официальная документация Android описывает `DynamicsProcessing` как effect, прикрепляемый к AudioSession ID; сам факт такой привязки не обещает sample-accurate synchronization двух независимых приложений. Не обещать идеального совпадения по одним transport clock-трассам.
