2. RASKOL «Нас не понимают вообще» (alias `113`, track `42884423`, album `5685525`) запущена после «Сохранёнки»: `STATE_BUFFERING` в 51.268с, `STATE_READY/isPlaying=true` в 52.820с. Далее ПО ВСЕМ КОМАНДАМ пользовательского Pause/Seek на видео родная Media3-сессия сообщает `isPlaying=true,playWhenReady=true,STATE_READY` вплоть до ухода в 78.7с; **в логе нет `SAME_ITEM_SEEK` для RASKOL**, хотя курсор источника делает скачки 59.475с→~57.7с, 63.82с→148.38с, 73.84с→152.77с. На видео (~60с) виден большой значок **Play** (UI Яндекса считает трек остановленным), в то время как из Media3 всё ещё приходит `isPlaying=true`. Это подтверждённое **расхождение Yandex UI и доступной стороннему приложению Media3-сессии**, а не плохой seek собственного декодера.

7. `replacement_original_muted`, `audio_owner_state state=REPLACEMENT`, `audio_decoder_start`: два независимых аудиотранспорта. Оригинал Яндекса активно проигрывается (громкость заглушена эффектом), наша замена идёт через отдельный `MediaPlayer`. CELIKOM **следует за Media3**; при расхождении Yandex UI и Media3 нельзя определить пользовательскую Pause/Seek из `isPlaying=true`, потому что именно эта ветка может быть ложной. Это и объясняет ощущение «Яндекс внизу продолжает, но без звука, а наша песня сверху не слушается кнопок».
8. **НЕТ ДОКАЗАТЕЛЬСТВ ФОРМАТА/DRM/ДРУГОГО АУДИОДВИЖКА ЯНДЕКСА:** логи показывают значения внешней Media3-сессии, но не исходные PCM/кодек Яндекса, не его внутренние UI события. Нельзя писать, будто именно codec/DRM, CDN, title или album являются доказанной первопричиной. Из фактов следует проблема согласованности UI→Media3 для некоторых треков/переходов; механизм внутри закрытого Яндекса остаётся неизвестен.

## Что делать дальше
**Не выдавать ещё одну APK из догадок, не возвращать Test.56 под видом нового исправления.** Сохранить подтверждённый звуковой эталон Test.50 неизменным. До следующих пользовательских испытаний требуется обоснованный путь получения достоверного состояния реальных Play/Pause/Seek действий для официального Yandex Music без root, Accessibility, Notification Listener и других запрещённых разрешений; либо доказать, что такой путь в Android 13 для данной Yandex версии отсутствует. Проверить read-only legacy MediaController/MediaSession *если* текущая реализация может подключиться: в старых логах Browser может возвращать unavailable; не создавать второй Media3 controller и не делать разрушительное переподключение.
Отдельная, вторичная задача: если есть надёжный и узкий способ, поправить условие единственной попытки восстановления зависшего BUFFERING (учитывать длительность отсутствия READY, а не позицию), но не путать это с исправлением UI-паузы: транспортные команды могут игнорироваться Яндексом.

**Архитектурное ограничение:** для стороннего приложения без специального разрешения доступны только те события состояния, которые Яндекс публикует; анонимное число AudioPlaybackConfigurations не даёт достоверной атрибуции источника/пальца и в Test.53 уже ломало хорошие песни. Не повторять эти эвристики.

Код, stable, backend, API, Hostinger и исходный эталон при составлении этого forensic не менялись. Предстоит перенос с Hostinger на другую платформу через MCP; приложить этот документ к передаче.
