## Independently researched public GitHub implementations

1. **PC YandexMusicLiberty**: https://github.com/gagayhhad-tech/YandexMusicLiberty . In `src/mod/features/ym-liberty/ym-liberty.ts`, the mod hooks the *internal* Yandex `GetFileInfoResource.getLocalFileDownloadInfo(trackId,...)`, returns a replacement `urls:[url]` inside the original player pipeline and avoids any two independent sound streams. Precise source: https://github.com/gagayhhad-tech/YandexMusicLiberty/blob/master/src/mod/features/ym-liberty/ym-liberty.ts . **Desktop-specific in-app injection; not callable from our standalone Android app.** PC CELIKOM works — do not change it.
2. **YM Liberty Android**: https://github.com/gagayhhad-tech/ym-liberty-android . This is **an independent Android Yandex player**, not a companion observer. `android_app/assets/www/yandex.js`: knows `trackId` from its own Yandex catalogue/API, checks `ym-liberty-db` and chooses replacement `streamUrl` *before playing*. `android_app/assets/www/app.js`: preloads the next audio URL in a second browser audio player and only crossfades when incoming `readyState>=2`. Sources: https://github.com/gagayhhad-tech/ym-liberty-android/blob/main/android_app/assets/www/yandex.js and https://github.com/gagayhhad-tech/ym-liberty-android/blob/main/android_app/assets/www/app.js . It cannot directly identify Yandex's current track from another app, and its two-player crossfade is between its *own* song transitions, not phase-verified overlay replacement. Android repo is GPLv3: do not copy code directly into an incompatible closed codebase without reviewing licensing.
3. **ChromaSync-Mobile**: https://github.com/Desai0/ChromaSync-Mobile . Closest **product-level** goal: same Yandex interface with substitute audio, *but achieved by app patcher or LSPosed in-process modification*. Its README says original plays until a replacement file is fully downloaded; later play uses cached substitute. The public repository currently has **only README, not the Android implementation source**, so no drop-in engineering fix or proof of Android acoustic performance exists. Do **not** propose app patch/root as if compatible with owner's permissionless ordinary APK requirement. Relevant insight: a deliberate **original-until-ready contract** is preferable to promoting an underbuffered stream then falling back repeatedly.
4. **Yandex Music Slopless**: https://github.com/bbird1980/yandex-slopless-app . ## Approved Android redesign direction — prioritize one coherent test APK

1. **Preserve user-visible behavior and track resolution**; no new source permissions, account login, patched Yandex app, external replacement player or changed PC architecture.
2. **Separate PREPARE (original fully audible) from AUDIBLE OWNERSHIP.** For sparse `BufferedAudio`, don't call stream-ready after 1×128KiB a proof of *playable future runway*. Track position-aware fully verified contiguous decoder-neighborhood bytes, ensure ongoing foreground-prioritized prefetch during the original-audible warm phase, and only grant when the decoder clock advances within drift tolerance **and** enough actual data is available. A finite readiness deadline keeps the source stable; no unsafe indefinite decoder ownership if no network runway. Optimize cached/primed tracks separately to preserve existing ~0.5s joins. Complete-file-before-first-play is the safest Chroma-inspired fallback, **but not mandatory for every track**: weigh owner preference for immediate replacement and bandwidth empirically.
3. **One owner-transfer state machine** for first join, post-pause resume, re-seek and buffer recovery: no `exclusive_single_turn` 0ms full-volume regrant while original is audible; effect/decoder not torn down repeatedly on one seek; guard against stale callbacks and track/account changes. Existing verified hot cached seeks should stay inside playing decoder. No tuning millisecond gains without eliminating the starvation/regrant logic.
4. **Avoid crossfading unsynchronized PCM by assumption.** Two independently clocked sessions are not sample-phase aligned merely because metadata and positions match. First-join `50/50` commands are proven but acoustic continuity is not. Test audio transitions using an appropriate actual sample-domain harness or acknowledged on-device evidence; preserve honest limitation of system-level DSP. If wholly eliminating two-session overlap were ever required, that would constitute a separate architecture/permissions/product choice.
5. **Seek correctness:** distinguish user finger event publication delay from Media3 source snapshot, native decoder ACK, and audible resumed clock. The RASKOL UI / Media3 discrepancy is not addressed solely by changing 128/256KiB Range or `seekTo` timeouts. Test stale pause/buffering, fast forward/back, same-song repeated actions and album-next boundaries; do not implement a heuristic that spuriously seeks on metadata noise.
6. **Automated regression gates:** reproduce zero-ramp regrant after transient buffer; a sparse source ready with one block then starving after two seconds; slow/late range requests competing with actual seek; source original remains audible until genuine ready; track change and stale callback cannot grant previous song; repeat hot cached seek remains low-latency; Bluetooth route/pause fail-open; counters distinguish first joins from seek resumes. Run existing full Android/host CI, verify APK package/versionCode/signer. Owner acceptance still pending until real phone test.
