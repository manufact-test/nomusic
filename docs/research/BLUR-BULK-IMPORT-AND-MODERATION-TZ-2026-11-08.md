## 1. Автоматический импорт: одну задачу на 100 или 150 песен, внутри партии по 50
**Цель:** владелец одной командой запрашивает 100/150 песен. Программа сама составляет 2/3 последовательных партии **по 50 пригодных файлов**; при техническом отказе берёт следующего ещё не использованного кандидата. Позже допустим запрос на 200 = 4×50. Никаких 10 отдельных ручных запросов по 20.

1. Перед запуском создать pinned manifest источника с Track ID/название/исполнитель/размер/Git blob SHA1 и зафиксировать SHA коммита. Вести общий machine-readable ledger по всему исходному набору; не начинать отсчёт «1500 новых» без проверки.
2. Для каждого кандидата: точный Yandex Track ID, fresh live DB проверка tracks, track_replacements всех статусов, track_requests и похожего artist+title; не затирать активные, pending и уже одобренные версии. Совпадение названия под другим ID = отдельная проверка, не автоматическое одобрение и не слепой пропуск.
3. Скачать только в временную среду GitHub Actions; проверка ожидаемого размера и Git blob SHA1, реального MIME, MP3 строгим Celikom\Application\Mp3Inspector (как на живом API), ffprobe для независимой диагностики, длительность; удалить промежуточные файлы после обработки.
4. Если Mp3Inspector/MIME/хеш не проходят — записать в **постоянный реестр пропусков** со стадией, Track ID, именем, причиной, источником и ссылкой; взять следующую песню из резерва. **Не объявлять файл испорченным**, пока не установлена причина. Не ослаблять существующий инспектор и не перекодировать исходник вслепую. Для отдельного анализа таких MP3 — сначала определить точную причину, затем проверить безопасный вариант исправления на копии и в CI, ничего не ломая у уже играющих записей.
5. Длительность относительно оригинальной записи Яндекса проверять только при наличии достоверных метаданных для конкретного Track ID. Сейчас часть импортированных треков имеет записанную длительность самого исходного MP3; **это не независимая проверка совпадения с Яндексом**. Если данных нет, ставить в ledger и интерфейсе заметку «оригинальная длительность не подтверждена», не объявлять проверку пройденной.
6. Перемещать проверенный файл **в своё приватное хранилище Hostinger**, не строить проигрывание через внешний GitHub, создавать только track + asset + replacement status=pending, is_active=0 через проверенный путь. Не выполнять approve/activate, не выставлять rights_confirmed за человека.
7. Батч по 50 — логическая партия, а не одна опасная гигантская SQL-транзакция. Идемпотентность по Track ID/хешу; возобновление после сбоя без дублей и повторных начислений. В рамках одного запуска сериализовать записи в production, ограничивать число параллельных скачиваний. Не менять существующие ветки Android, Windows/desktop, расширения.
8. На каждый блок в 50 и весь запрос дать короткие итоги: запрошено, новых pending, уже есть, pending до импорта, технически отклонено, добраны резервы, осталось без кандидата, bytes, download/transfer/import/end-to-end seconds, прямые ссылки на заявки и CSV проблем. Отдельно подтверждать live DB после записи, не ограничиваться зелёным Actions.
9. Перед крупной партией проверять доступное место в приватном хранилище и лимиты GitHub Actions/Hostinger. Не делать 100–150 новых записей в production, пока нет очередного прямого запроса владельца на загрузку такого объёма.

**Где начать:** `tools/blur-batch20/download_sources.py`, `tools/blur-batch20/import-pending.php`, `.github/workflows/blur-batch20-pending-import.yml`, `tools/blur-batch20/batch20.json`. Текущие скрипты жестко привязаны к 20 ID, их надо сделать параметризованными/однократно запускаемыми, с журналом и продолжением, а не копировать 3 workflow для трёх партий.

## 2. Админка — массовое выделение, одобрение и удаление
**Цель:** владелец открыл «Загруженные версии → На проверке», показал 50 элементов, нажал «Выделить все 50», подтвердил, что действительно проверил аудио/права, одобрил всю выделенную пачку одним действием. Аналогично можно отклонить или удалить непригодные записи оптом.

**Фактическая основа:** `server/src/Admin/AdminPanel.php` уже умеет 10/25/50 записей на странице, проигрывать через приватный /admin/audio/{id}, имеет CSRF и отдельную галочку `rights_confirmed`; `server/src/Admin/ModerationService.php` проверяет rightsConfirmed на approve и защищает status/expected_active. Заново админку не писать.

**UI и поведение:**
- Чекбокс на каждой карточке pending; «Выделить все на странице», «Снять выделение», индикатор «Выбрано N из 50», панель «Одобрить», «Отклонить», «Удалить». Ничего не выбрано по умолчанию. Фильтры/пагинация/ПК и телефон сохраняются; существующие одиночные действия не ломать.
- При массовом одобрении — отдельное подтверждение с перечнем/количеством, **неотмеченная по умолчанию обязательная галочка** «Подтверждаю, что лично проверил выбранные записи, их качество и права на использование». Без галочки изменения запрещены на сервере, а не только в JS. Уместный общий комментарий. Текущая логика approval может сделать версии активными; сделать это только по явному подтверждению владельца, никогда при импорте.
- «Отклонить выбранные» — обязательная общая категория (дубликат/не тот трек/качество/права/другое), комментарий при необходимости, массовая отметка rejected и аудит по каждому ID.
- «Удалить выбранные» — **отдельное опасное действие, только для владельца** с повторным подтверждением и числом объектов. Сначала безопасно отклонить/изъять из pending; если пользователь выбрал «удалить навсегда», удалить физическое private audio только при отсутствии других ссылок на тот же audio_asset; не стереть активное/одобренное или общий файл и не сломать foreign keys. Сохранить минимальный tombstone/audit и лог Track ID, чтобы файл не вернулся при повторном массовом импорте без решения. Два действия не смешивать.
- Защита: роли и CSRF, max 50 IDs в одном POST, валидный список уникальных положительных ID, recheck статуса/версии и current active под блокировкой для каждого трека, никакого доверия к присланным клиентом статусам или rights flag без явного POST. Параллельная модерация не должна перезаписать изменения.
- Не делать «молчаливого успеха», если прошло 49 из 50: показать отдельно успешные/пропущенные/конфликтные IDs, возможность обновить очередь и повторить только провалившиеся. Аудит admin_id, время, решение, общий batch/action id, причина; корректность бонусов за вклад сохранить.

**Тесты приёмки:** изолированная MySQL база со 50 pending; выбор 1/50 и все 50; approve без галочки ⇒ 0 изменений; с явной галочкой ⇒ ровно выбранные одобрены/активированы; bulk reject с причиной; bulk hard delete отклонённых/неиспользуемых ассетов; блокировка active и общих файлов; CSRF/неавторизованный/чужая роль; конкурентная модерация; аудит/начисления; реальная адаптивная проверка desktop+mobile. После CI один безопасный деплой backend/админки отдельным утверждённым путём и приёмка владельца. Не делать массового реального approve в тестах.

## 3. Постоянный реестр всего источника и список того, что владелец будет искать вручную
- Источник истины: `docs/research/BLUR-REJECTED-CUMULATIVE.csv`. **Сейчас 7 технически отклонённых Track ID**, а не четыре: четыре из первой двадцатки + три резервных. У всех отдельных песен собственные Track ID и ссылки для поиска.
- `docs/research/BLUR-SKIPPED-DUPLICATES.csv` — отдельно 3 проверенных дубля. Дубли и уже существующие заявки **НЕ включать** в список песен, которые требуется найти вручную.
- После КАЖДОЙ партии автоматически **добавлять**, а не перезаписывать историю: external ID, artist/title, source blob SHA, причина/cause, etapa/run, дата, ссылка Яндекс, попытка/замена, manual_resolution, итог. Новая версия успешна ⇒ помечать original issue resolved, но историческую неудачу не удалять.
- Финальный файл по завершении обработки всего исходного pinned набора: Excel и CSV **только с нерешёнными недостающими песнями** — несовместимые/отсутствующие источники, невалидные метаданные, неизвестные права/длительность, для которых нет допустимой версии. Отдельная сводка со статусами imported/existing/pending/manual_needed и идентификаторами, чтобы ни одна исходная песня не исчезла между батчами.
- Сейчас нельзя утверждать, что все ~1500 гарантированно новые, что у всех есть права и что можно автоматически одобрить их. Цель — провести каждый исходный ID через учёт: импортировать допустимые и дать владельцу полный список остальных для ручного поиска.

## 4. Границы работы и приёмка
- В этом документальном заходе новые 100–150 песен **не загружались**, массовая админка **ещё не реализована**. Следующий чат делает код и реальные CI, не пишет «готово» без результата.
- Рабочая ветка импорта feature/blur-batch20-20261108 исторически от Android feature snapshot — **никогда не сливать её целиком в main**. Для интеграции правок админки переносить только конкретные серверные файлы в отдельную актуальную backend ветку по согласованию с текущим серверным разработчиком, не захватывая чужие APK или Windows код.
- Перед изменениями production проверить актуальный HEAD, работающий release и других активных агентов. Хранить приватные SSH ключи только в GitHub Secrets; не раскрывать.
- Доказательства: CI + отдельная read-only сверка реальной БД после write и проверка в интерфейсе; в конце дать человеку только что реально сделано, что осталось проверить, ссылки и короткую сводку.
