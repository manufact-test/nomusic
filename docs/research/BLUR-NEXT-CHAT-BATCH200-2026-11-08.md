## Большой следующий рабочий блок — 200 новых

1. **Сначала расширить candidate pool.** Текущий `tools/blur-batch50/candidates.json` содержит только **250 исходных** и уже использован в предыдущих импортах. В предыдущей предварительной проверке 100 исходников из 106 пригодных попыток, при этом 75/250 были пропущены из-за существующих записей/совпадений. Не обещать ещё 200 из этого же файла. Найти ещё источники внутри **закреплённого** репозитория или создать новый проверенный pinned manifest; для каждого ID записать artist/title, Git blob SHA1, размер. Не брать неустановленные или произвольные URL без проверки происхождения; не загружать файлы из общего интернета, если права/происхождение сомнительны.
2. До скачивания сделать **read-only SELECT на живом Hostinger**: `tracks`, `track_replacements`, `track_requests`, `bulk_moderation_tombstones`, совпадение artist+title, ранее импортированные Track ID, накопительный CSV отказов. Запретить дубли по ID и названию; учитывать резервные кандидаты на случай битых MP3/OGG.
3. Сформировать **ровно 200 проверенных новых** аудиозаписей; сверить MIME `audio/mpeg`, Git blob, размер, `Mp3Inspector`, `ffprobe`, duration. Недоступные/неподходящие не терять: технические отказы в **одном накопительном CSV** по Track ID (без дубликатов), временные сетевые ошибки — отдельно.
4. **Зафиксировать конкретные 200 ID в отдельном неизменяемом `fixed-plan200.json`** до production запуска. Никакой «добор новой сотни» при повторном workflow после частичного успеха. Перезапуск должен работать **идемпотентно** и повторять только эти 200.
5. Запуск на Hostinger **четырьмя последовательными партиями 50**. Перед каждой проверять актуальный active release, свободное место, источники и `dry-run=0 writes`; загружать только в приватное хранилище. После каждой партии отдельный независимый live SELECT: `50 pending, 0 active, 0 auto-approved`, факт наличия файлов. Технически успешный блок может быть завершён независимо от последующего блока; писать явную сводку по 1/2/3/4.
6. После четвёртой партии **независимая итоговая проверка всех 200**, без записей в production, а также проверить admin pending по 50 на странице. Предоставить ссылку на GitHub Actions, IDs, объём, новые отказы и короткий отчёт; **не нажимать массовое одобрение за владельца**. После ручного одобрения отдельно проверять catalogue / resolve / HEAD / Range, как это сделано для 100.
7. **Изоляция обязательна.** Продолжать в новой `feature/blur-batch200-...` от `feature/blur-batch100-20261108`. Не трогать `main`, рабочие ветки Android/desktop/extension, не выкатывать непроверенный `AdminPanel.php` на production. Админские bulk-действия уже отдельно установлены guarded patch на сервере; перед любым чужим деплоем сверить live состояние.

## Ограничения и критерий завершения

- Источник может не иметь достаточного числа подходящих треков; **если 200 уникальных не набраны, не заявлять успех** и не придумывать файлы.
- Никакого одобрения/активации и автоматической декларации прав; эти действия делает человек.
- Не считать аудио подходящим только по валидному MP3: соответствие оригинальным метаданным/длительности Яндекс.Музыки не было независимым образом подтверждено.
- Для 200 могут понадобиться дополнительное дисковое пространство и поддержка более длинного GitHub Actions workflow (100 заняли ~590 MB). Проверять перед загрузкой, без угадываний.
- Итог пользователь любит **краткий и честный**: что реально загружено, проверено, что осталось не проверенным, какие новые файлы в CSV, что ему надо сделать.
- Задание на 200 — **намерение владельца для следующего чата**, здесь никаких новых песен не загружено.
