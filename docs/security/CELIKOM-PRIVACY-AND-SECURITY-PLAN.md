# CELIKOM — регламент приватизации и безопасности

**Согласовано владельцем 21.11.2026. Статус: план утверждён, исполнение не подтверждено. Внутренний документ.**

Основание: Master ТЗ MVP v1.5, план работ v1.6 (этапы 14 и 18), SECURITY.md, docs/runbooks/stage14-hardening.md, аудит distribution/support-export, актуальные Android и Windows handoff. Этот регламент дополняет, а не заменяет документацию продуктовых линий. Целевой путь в закрытом репозитории: `docs/security/CELIKOM-PRIVACY-AND-SECURITY-PLAN.md`. Не публиковать в открытом репозитории.

## 1. Неизменные условия

- Максимальная законная публичная приватность владельца; защита исходников, музыкального каталога, пользовательских данных, секретов и платежей. Не обещать абсолютную анонимность, невозможность копирования или обход обязательной идентификации продавца.
- Существующая модель работы сохраняется: ChatGPT Plus, обычные чаты проекта, подключённый GitHub, чтение → правки → коммиты → тесты → сборка → передача готового файла владельцу. Не переходить на Work, Business, платный OpenAI API или новый платный сервис без согласия владельца.
- GitHub остаётся закрытым инструментом разработки; вычисления по возможности переносятся на self-hosted runners. FlokiNET Romania VPS III и домен celikom.com — новый production-контур. Forgejo и собственный MCP не являются частью согласованного решения.
- Не увеличивать фиксированные расходы. Платное превышение CI-лимитов исключить; storage, трафик и платёжные комиссии учитывать отдельно. Не покупать вычислительные ресурсы заранее.
- Продолжаются ВСЕ линии: Windows, Android A1, расширение, backend, сайт и админка. Не менять архитектуру приложений, не сбрасывать данные, не начинать исследования заново, не чистить старые ветки/PR без отдельного разрешения. Участие владельца минимально.
- Цель — готовность к коммерческому запуску в понедельник 23.11.2026; дата не отменяет обязательных проверок, прав на контент и одобрения платёжного провайдера. Не обещать приём средств без подтверждения готовности.

## 2. Рабочие точки и сохранение совместимости

- `manufact-test/nomusic`: непосредственно перед операциями получить фактические HEAD всех активных веток. Windows: единственная каноническая линия `main`, принятая версия 0.24.54.0; документ `docs/windows/NEXT-CHAT.md`. Сохранить immutable backup перед W173. Не повторять принятую работу без конкретного основания.
- Android: единственная активная ветка `experiment/android-a1-metrica-init-state-observer-arm13-20261112`, handoff `docs/android/CELIKOM-A1-NEXT-CHAT-START-2026-11-21.md`. BETA12 — последняя известная пакетная точка; реальная подмена на телефоне не подтверждена. Сохранить native ARM64 проверки, текущую стратегию и диагностику; не объявлять зелёный CI доказательством воспроизведения.
- Backend, сайт, расширение: определить фактически развёрнутые и принятые ревизии по актуальным данным, а не старым номерам версий. Сохранить обе базы, если сайт/CMS и API используют отдельные экземпляры, все каталоги, аккаунты, сессии, trial, подписки, награды, промокоды, обращения, объекты аудио, gain, статусы и связи.
- Сохранить ключи подписи и идентификаторы приложений, цепочку автообновлений, контракты API, HTTPS, CORS, signed audio/Range, поддерживаемые форматы, fail-open, ручную модерацию. Старые клиенты должны переходить на новый сервер без нарушения работы; проверить прежний origin и управляемый переход до отключения Hostinger.

## 3. Приоритеты и последовательность

P0 — обязательно до соответствующего production-переключения/коммерческого запуска; P1 — усиление после обязательных ворот, без остановки разработки. Все пункты открыты до подтверждения проверкой.

### P0. Закрытие GitHub и непрерывность разработки

1. Владелец переводит репозиторий в Private через Settings; изменение visibility через текущий коннектор не поддерживается. Проверить фактический статус.
2. Проверить доступ из обычного чата к закрытому репозиторию: чтение, безопасный тест записи, коммит, ограниченный workflow и получение результата. Не отключать прежний контур до проверки.
3. Проверить существующие форки, публичные релизы, артефакты, Issues, Actions-логи, историю на предмет случайно опубликованных секретов, данных и медиа. Отозвать/заменить скомпрометированные доступы. Приватизация не удаляет чужие копии и публичные форки. Не удалять историю произвольно.
4. 2FA на аккаунтах, ревизия приложений/доступов, минимальные разрешения, отдельные отзывные CI-credentials. Секреты не публиковать в Git, чате и логах.

### P0. Резервирование перед изменениями

- Зашифрованный Git mirror/bundle всех веток и тегов; отдельно метаданные релизов/PR, нужные артефакты, LFS при наличии, контрольные суммы и манифест. Не считать mirror полноценной копией всех GitHub-сущностей.
- Консистентные дампы БД, приватное аудио, конфигурации, существующие ключи и релизные файлы. Инвентаризация размера, схем, хешей и прав доступа; изолированное пробное восстановление.
- Не менее одной копии вне FlokiNET; использовать имеющееся место или компьютер владельца, шифровать до передачи. Ключи восстановления хранить отдельно. Не использовать публичные workflow-артефакты для production-данных.

### P0. Подготовка FlokiNET

- Проверить реальную ОС, архитектуру CPU, RAM, свободное место, сеть, виртуализацию и лимиты тарифа; размеры БД/аудиотеки и запас места для backup/build. Ubuntu LTS, Nginx, совместимый PHP (проверить текущую версию), совместимый MySQL/MariaDB, бесплатный TLS.
- Отдельные системные пользователи и права сервисов, firewall, SSH по ключам (парольный вход отключать только после проверки альтернативы), обновления безопасности, защита от перебора, закрытый внешний MySQL, минимальные открытые порты. Проверить IPv4 и IPv6. Ограничить доступ к админке; предусмотреть 2FA и безопасное восстановление.
- Секреты вне document root и репозитория, права доступа минимальные. Не раздавать через веб .env, .git, дампы, бэкапы, исходники backend и внутренние журналы. Отдельно проверить ротацию логов, отсутствие signed URL и персональных данных в логах. Мониторить health, свободное место, RAM, ошибки и срок TLS.

### P0. CI/CD без роста расходов

- Инвентаризировать реально используемые workflows и триггеры, не заменять массово runs-on. Установка Linux self-hosted runner по официальной инструкции; отдельный непривилегированный аккаунт, изоляция от production, ограничения CPU/RAM/диска, только доверенные задачи. Не добавлять runner в привилегированную docker-группу с доступом к хосту; изолированные тестовые сервисы там, где необходимы. Не разрешать выполнение непроверенных PR с секретами.
- На FlokiNET: backend, сайт, расширение и совместимые Android APK-задачи после нагрузочной проверки. Сервер с ограниченной RAM не считать гарантированно пригодным для тяжёлых сборок одновременно с production.
- Windows: сохранить нативную Windows-среду, .NET/Inno Setup, тесты установщика. Возможен runner на компьютере владельца только при его согласии и безопасной изоляции. Android A1: сохранить ARM64-native gate, не заменять его x64-сборкой. Для специализированных задач использовать совместимые runners в границах бесплатного бюджета; обеспеченность неограниченными бесплатными ARM64/Windows-ресурсами пока не доказана.
- Проверить актуальные условия тарификации GitHub и поставить ограничение платных расходов. Не обещать полный бесплатный цикл до проверки всех платформ. Готовые релизы хранить отдельно с контрольными суммами; ограничить кеш/retention GitHub. Сборочные ключи выдавать только нужной защищённой операции; не передавать production DB/платёжные секреты runner.

### P0. Переезд production с Hostinger

- Развернуть параллельный новый контур, импортировать копии без воздействия на старый. Сохранить существующие API и StorageAdapter/BillingAdapter, настройки почты, авторизацию и миграции. Проверить соответствие схем данных, количества строк и аудиохешей, отношения между сущностями и права.
- Проверить сайт/CMS, загрузку/модерацию, регистрацию/вход/сброс пароля, поддержку, доступ, промокоды, награды, инциденты, отдачу аудио и релизов.
- Перед переключением остановить или согласованно синхронизировать записи, выполнить финальный консистентный перенос; исключить split-brain, двойные записи и потерю платежей. DNS/HTTPS celikom.com, проверка старых клиентов, rollback-план. Старый хостинг не выключать до подтверждения устойчивости и восстановления. Не накатывать старую БД поверх новых платежей/пользовательских данных при откате.

### P0. Аудиотека и каталог

- Файлы вне public root, приватные storage keys через существующий StorageAdapter. Серверная проверка auth/entitlement, краткоживущие scoped signed URLs; проверка срока и подписи. Не публиковать прямые ссылки, дампы, полный каталог или сырые медиа.
- Проверить анонимный отказ, доступ к чужим данным, перебор идентификаторов и массовые запросы, rate limits/anti-abuse с учётом NAT, VPN, Range/HEAD и нормальных клиентов. Не ломать seek, crossfade, gain, fail-open. Проверить signed URL redaction, CORS, отсутствие листинга и доступов к файловой системе.
- Сохранить ограничения/валидирование upload, декодирование, дедупликацию и ручную модерацию pending → approved. Права на коммерческое использование и процедуру удаления контента подтвердить отдельно. Не обещать невозможность записи воспроизводимого звука; не вводить тяжёлый DRM без доказанной необходимости.

### P0. Пользователи, админка и публичная приватность

- Проверить серверную авторизацию каждого endpoint, разделение ролей, объектный доступ, защита паролей/сессий, отзыв токенов, brute-force, SQLi/XSS/CSRF, безопасные cookies, admin 2FA, ограничение попыток и аудит действий без утечки секретов.
- Минимизация персональных данных/аналитики, сроки хранения, удаление/выгрузка аккаунта с учётом обязательств, политика конфиденциальности и применимые требования GDPR. Сохранять безопасный диагностический экспорт и проверять redaction на всех платформах.
- Проверить публичные данные домена, профиля GitHub, метаданные релизов, изображений и документов, разделить публичную контактную почту CELIKOM и личную. Удалять только необязательные сведения; не фальсифицировать обязательные данные о продавце, не скрывать их от провайдера или регуляторов.
- ChatGPT: сохранить текущий проект и историю, проверить 2FA, отключение улучшения модели в настройках Data Controls по выбору владельца, ревизию публичных ссылок. Не отправлять production-пароли, приватные ключи и полные базы в чат. Не полагаться только на память: документация закрытого репозитория — источник истины.

### P0. Оплата и коммерческий запуск

- Существующий BillingAdapter, hosted checkout; данные карт не хранить. Убедиться, что конкретный провайдер одобрил продавца/модель сервиса, прошёл KYC/KYB при необходимости и поддерживает необходимые способы оплаты. Проверить права на коммерческое распространение аудио и обязательные сведения/условия подписки, возвраты, отмену, privacy, налоги и чеки по применимым требованиям.
- Проверить webhook signature, уникальность provider event ID, идемпотентность и повторные/неупорядоченные события. Серверный ledger и entitlement — источник истины, не доверять redirect. Checkout, успешный/неуспешный платёж, продление, отмена, возврат/chargeback и отзыв доступа проверить на тестовых данных, затем контролируемой реальной оплатой при разрешении.
- До подтверждения этих ворот не принимать деньги. Не обещать Android-функциональность, не принятую владельцем. Разработка Android продолжается независимо от даты коммерческого запуска.

### P0. Бэкапы, эксплуатация и откат

- Целевые интервалы: БД каждые 6 ч (платёжные данные при необходимости чаще), аудио ежедневное инкрементальное, Git ежедневно, конфигурация после изменения, полный backup еженедельно, ключи отдельной зашифрованной копией. Проверка восстановления ежемесячно и до первого переключения. Уточнить RPO/RTO по фактическому размеру и нагрузке; проверить полноту бэкапов и сигнализацию об ошибках.
- Документировать безопасную процедуру rollback, инциденты, отзыв ключей, восстановление доступа и действия при утечке. Независимая копия и восстановление обязательны, backup на том же VPS недостаточен.

### P1. Усиление защиты клиентских сборок

- Chrome: минификация, исключение source maps и development-файлов. Windows: release-упаковка, выборочная обфускация только с регрессиями. Android: R8/ProGuard для совместимых частей, сохранить native/reflective contracts. Не хранить клиентские секреты, критические проверки только на сервере. Сохранить подписи и обновление поверх текущих версий. Публикуемый клиент может быть исследован; обфускация — дополнительная мера, не граница доверия.
- Уточнить ресурсные лимиты по реальной нагрузке, расширить мониторинг, периодические dependency/security checks, нагрузочные испытания и ревизию доступов. Не считать security runbooks или CI доказательством полного pentest.

## 5. Участие владельца и правила следующего чата

Ассистент: готовит команды, документацию, код и проверки в пределах доступных инструментов; не просит владельца делать то, что может сделать сам. Не заявлять выполненное без результата проверки.

Первое действие: проверить visibility репозитория и доступ из обычного чата. После подтверждения Private добавить этот документ в `docs/security/`, зафиксировать его коммитом без изменения приложения. Затем двигаться по регламенту, вести краткий статус прохождения ворот и сохранять актуальные handoff. Если новый факт конфликтует с планом, объяснить конфликт и согласовать существенное изменение, не менять стратегию молча.
