# CELIKOM — возврат к GitHub Actions и сохранение FlokiNET (26.11.2026)

**Статус:** решение владельца принято 26.11.2026. Реализация, восстановление CI и приёмка клиентов **не подтверждены**. Переключение видимости репозитория — отдельное ручное действие владельца.

## Почему меняем план

После миграции с Hostinger на FlokiNET привычный цикл разработки, сборок, тестирования и выдачи новых версий Windows, Android и расширения оказался нарушен. Цель — восстановить рабочий выпуск продукта без нового переноса API/сайта/музыки/БД и без очередного переустройства архитектуры.

Владелец решил временно открыть `manufact-test/nomusic` для возврата GitHub-hosted Actions; после стабилизации снова закрыть исходники и оплачивать необходимые Actions. Это временная тактика восстановления, а не решение распространять CELIKOM с открытым исходным кодом.

**Проверка GitHub при фиксации решения:** `manufact-test/nomusic` ещё имел статус `private`. Не писать, что он уже открыт, пока видимость не подтверждена повторно.

## Утверждённая рабочая схема

1. **GitHub `manufact-test/nomusic` — канонический исходный код, разработка, CI, сборки и автоматические тесты.** При необходимости использовать соответствующие GitHub-hosted Windows/Linux/ARM окружения. Не считать одну Linux-машину FlokiNET полноценной заменой Windows/ARM. Не обещать отсутствие квот, лимитов или затрат без проверки текущего GitHub Billing.
2. **FlokiNET — основной продакшен и источник клиентских файлов:** API, сайт `celikom.com`, база, музыкальное хранилище, релизные указатели, доставляемые APK/EXE/ZIP и механизмы обновления. Сохранять существующее приватное Forgejo/зеркало и резервные копии; не вводить вторую каноническую ветку.
3. **Hostinger — не возвращать как основную площадку**, но не отключать его оставшиеся зависимости, прежде всего обновление уже установленного legacy Android, до доказанного перехода. Не переносить сервисы заново только из-за проблем CI.
4. **Self-hosted runners на FlokiNET** и текущие заготовки публикации не удалять вслепую. Они не являются обязательной средой всех сборок: можно вернуть GitHub-hosted CI там, где он надёжнее. Не давать CI прямые root/SSH/production-секреты; доверенный серверный публикатор должен отдельно проверять и принимать сборку.
5. **Без дополнительных аккаунтов, организаций и нового переезда.** Исправляем имеющиеся workflows, тесты и каналы доставки, а не создаём инфраструктуру с нуля.

## Обязательный цикл выпуска

Изменение кода → автоматические тесты и сборка в GitHub → проверка версии, подписи/хеша и доступности на FlokiNET → **тестовая версия для владельца с celikom.com** → реальные пользовательские испытания/диагностика → **явное согласие владельца на выпуск конкретной версии** → публикация в соответствующий клиентский канал и проверка обновления установленной версии.

- Готовый GitHub artifact, «зелёный» CI, файл в приватном spool или ссылка в чат **не доказывают** работающую доставку/автообновление.
- Тестовые и клиентские `stable` указатели разделены; новая сборка не должна автоматически менять клиентский `stable`.
- Windows: отдельно проверять подписанный установщик и реальный переход установленного клиента с предыдущей версии.
- Android: различать A1 beta и legacy stable, проверять подписи/версионность и переход через старый Hostinger updater, пока он нужен.
- Расширение: owner ZIP и публикация для обычных пользователей — разные процессы; автообновление конечных пользователей зависит от Chrome Web Store. Не представлять owner ZIP как браузерное автообновление.
- Не проводить клиентский публичный релиз из открытого исходного репозитория в обход защитного правила [ADR-0002](../adr/0002-public-development-private-release.md). До коммерческого релиза — закрытие репозитория, проверка угроз и согласованный клиентский выпуск.

## Риски временной публичности

- Публичность раскрывает исходники, историю коммитов, метаданные авторства, workflows и потенциально журналы/артефакты Actions. После закрытия GitHub нельзя гарантировать исчезновение сделанных копий и раскрытых связей с людьми/другими проектами.
- **Перед открытием:** проверить активные файлы и историю на токены, ключи подписи, пароли, клиентские данные и ссылки на приватные внутренние ресурсы; минимизировать публичные логи/артефакты. Изъятие секрета из последнего коммита не отменяет ранее состоявшегося раскрытия; скомпрометированные ключи подлежат ротации.
- Публичные workflows, PR из форков, `pull_request_target`, artifacts и журналы — отдельная поверхность риска. Не передавать непроверенному коду доверенные секреты и привилегии публикации.
- Сохранить существующие контрольные точки и резервную копию перед опасными действиями; не переписывать историю, не массово удалять ветки/релизы и не переустанавливать сервер без конкретной необходимости.
- Решение о временной публикации принято владельцем с пониманием этих рисков; GitHub visibility переключает владелец, **не** CI.

## Приоритет работы после возвращения Actions

1. Проверить фактическую видимость репозитория и доступность GitHub-hosted runner. Сделать минимальные диагностические прогоны с контролем затрат, без бессмысленных повторных запусков.
2. Сохранить рабочие базовые версии и инвентаризировать workflows/артефакты/каналы обновлений. Ничего не объявлять исправленным без теста.
3. Восстанавливать и тестировать по отдельности Windows, Android и расширение. Актуальные непроверенные кандидаты и конкретные дефекты смотреть в [общем handoff](../handoff/NEXT-CHAT.md), [Android](../android/) и [Windows](../windows/). Для расширения на 26.11 идёт сбор диагностик прослушивания 0.4.87, без преждевременного клиентского релиза.
4. Проверить полную цепочку «GitHub build → FlokiNET HTTPS → скачивание → установка → обновление» и явно отделить автоматические проверки от подтверждения владельца.
5. Когда все три линии и процесс выпуска будут приняты владельцем — **закрыть репозиторий**, повторно оценить публичные следы/секреты, включить контролируемую платную GitHub Actions квоту. Оплату после первых доходов согласовать отдельно; пока без обещания фиксированного бюджета или сроков.

## Что переопределено, а что нет

Это более новое решение владельца **заменяет только прежнее требование постоянно держать `nomusic` приватным во время восстановления и избегать GitHub-hosted minutes любой ценой**, записанное в [решениях 22.11](../migration/CELIKOM-FLOKINET-DECISIONS-2026-11-22.md). Все требования к FlokiNET, безопасности, сохранению зависимостей, резервированию и раздельной публикации тестовых/клиентских версий остаются в силе. [ADR-0002](../adr/0002-public-development-private-release.md) о закрытии исходников перед релизом конечным пользователям также остаётся действующим.

**Не запускать новый инфраструктурный переезд ради этого решения.** Сначала вернуть работающую разработку, сборку, проверку и доставку каждой версии.
